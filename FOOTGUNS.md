# FOOTGUNS.md

Traps that already cost someone a round. Things that compile, parse, read or
look fine — and are wrong anyway.

**Grep this file the moment something behaves unexpectedly, before you start
debugging.** Entries are written so the words you would search for — an error
string, a symbol, a command — come first.

Tags:

- untagged — a live trap. It will bite you today.
- **[FIXED]** — it bit someone, it is now guarded. Do not reintroduce it; the
  entry records why the guard exists.
- **[DESIGN]** — a locked design decision not yet implemented. The trap is in
  building against the old assumption.

Add to this file whenever you lose time to something the next agent would also
lose time to. One line, mechanism first, cite the source.

## Zellij behaviour

Zellij's own source is the authority. Vendored at
`~/.cargo/registry/src/*/zellij-tile-0.44.3/` and `…/zellij-utils-0.44.3/` —
cite those by path and the next reader can grep them.

`zellij-server` is **not** vendored, so a claim about it has to say where it
came from. Two routes, both fine, and the citation itself says which was taken:

- **Observed live** → cite the C-section of
  [SUBSYSTEM-VALIDATION.md](docs/superpowers/spikes/SUBSYSTEM-VALIDATION.md)
  that records it. This is the only route for anything the source cannot
  settle — timing, event ordering, what actually happened on screen.
- **Read at a tag** → fetch it and cite `zellij-server/<path>:<lines>` the same
  way a vendored crate is cited, where `<path>` is the whole in-repo path,
  `src/` included, exactly as it appears in the citation:

  ```
  curl -sL https://raw.githubusercontent.com/zellij-org/zellij/v0.44.3/zellij-server/src/tab/layout_applier.rs
  ```

  Read a **tag**, never `main` — `main` is not the code running on anyone's
  machine, and a line number from it is worse than no citation, because it
  looks checkable and isn't.

  Which tag is the live question, and Cargo.lock does not answer it: the `=`
  pins fix the compile-time `zellij-tile`/`zellij-utils` crates, not the zellij
  binary the user runs. `doctor::TESTED_ZELLIJ` (0.44.3) is the version the
  ledger's behaviour is pinned to, and a mismatch there **warns, never halts**
  — so a session can legitimately be running a different server than the one
  every citation in this file was read at. Read the tag matching the server
  whose behaviour you are explaining, and say so when it is not 0.44.3.

A source citation says what the code *does*; a ledger citation says what clave
*saw*. When an entry has both, give both — that pairing is the strongest form,
and it is what distinguishes a mechanism from a symptom.

- **Plugin identity is `(location, configuration)` compared exactly — a miss STARTS A NEW PLUGIN rather than no-oping.** `impl PartialEq for RunPlugin` compares exactly `(&self.location, &self.configuration)` and `RunPlugin` derives `Hash` (`zellij-utils/src/input/layout.rs:518-526`, `:424-425`). A pipe or reload whose config does not match logs `"Plugin {} not found, starting it instead"` and spawns a second bar. This is the mechanism behind the v0.1.1 double-sidebar (#43/#44). Grep string when it happens: `not found, starting it instead`.
- **`PluginUserConfiguration::new` silently strips 14 reserved keys** — `hold_on_close`, `hold_on_start`, `cwd`, `name`, `direction`, `floating`, `move_to_focused_tab`, `launch_new`, `payload`, `skip_cache`, `title`, `in_place`, `skip_plugin_cache` (`zellij-utils/src/input/layout.rs:532-548`). A config key with one of those names is invisible to plugin identity, so it can never disambiguate two instances. Check this before adding a config key to fix a skew problem.
- **Zellij NEVER repaints an idle plugin — there is no clock anywhere in the render path.** `render` is called in exactly two places: after `update` returns `should_render == 1` for a delivered event (`zellij-server/src/plugins/wasm_bridge.rs:2156-2180`, tag v0.44.3), and on a resize that *actually changed* the pane's rows or cols (`:838`, guarded by `old_rows != new_rows || old_columns != new_columns || event_id == 0`). So a bar on a hidden or quiet tab can go minutes without a single render — and note the second site's guard: a resize zellij REFUSES produces no render either, so "wait one render and see if it moved" needs some other event to arrive. Any model logic whose CORRECTNESS waits for renders to accumulate is starved by construction. It shipped once: #137's storm brake refilled its allowance after three renders at rest, which turned a rate limit into a lifetime budget that 33 clean `Alt+c` presses exhausted, after which the sidebar stopped resizing (caught in review on PR #152, 2026-08-10). Laziness may key off renders; correctness may not.
- **`Event::TabUpdate` reaches only the ACTIVE tab's plugin instance** — hidden instances are event-starved: stale active flags, stale tab sets (a new tab is invisible to them), no observable transition. `PaneUpdate` likewise. Only pipes and store-snapshot pushes broadcast. (SUBSYSTEM-VALIDATION C3)
- **`is_active_instance()` is NOT a visibility gate** — every hidden instance's stale tab set claims its own tab is active, so anything gated on self-diagnosed "am I active" is poisoned during event bursts. Cost three rounds ending in an `EMFILE` server crash. The only trustworthy signal is the executor gate (own tab == replicated beacon). (C6 rounds 11–13)
- **`render()` is not visibility-gated either** — every instance renders at least once after load, so "hidden panes never render" holds only in steady state. A render-driven announce crashed the server with EMFILE on the first Alt+c (252 announces, 460 events in one second). (C6 round 13)
- **`resize_pane_with_id` silently refuses fixed-size panes — `CantResizeFixedPanes`.** It flashes "FIXED!" on the pane; the plugin sees nothing. Layout sizes must be percentages (`size="15%"`), in all three generators. (C6/C8)
- **zellij emits NO events for plugin-initiated resizes** — the only feedback is the plugin's own `render()`. Cross-tab width healing is structurally blind. This killed the entire repair-by-command architecture. (C6 rounds 10, 18)
- **`show_self()` is a focus action** — the server maps it to `Action::FocusPluginPaneWithId`, which switches to that pane's tab; ten hidden instances calling it is ten racing focus actions. Use `show_pane_with_id(PaneId::Plugin(own), false, false)` → `UnsuppressOrExpandPane`. (C6 round 14)
- **`suppress_pane` damages the tab's swap state, so `swap_tiled_layout` can never restore an unsuppressed pane** — `suppress_pane` → `extract_pane` → `set_is_tiled_damaged()`, and `add_tiled_pane` auto-relayouts only when NOT damaged. Other damage-setters: `resize_pane_with_id`, `resize_whole_tab`, close/extract/splits. The swap layout parsed perfectly and never fired. (C6 round 19)
- **A floating pane can never cover the bar — `set_selectable(false)` already fenced it off, so any "clear the sidebar" geometry is arithmetic for a problem that does not exist.** `offset_viewport` resets the viewport to the display area and then, for every **non-selectable** pane flush against an edge and spanning the perpendicular axis, moves that edge past it (`zellij-server/src/tab/layout_applier.rs:1032-1075`). `clave-bar` is full-height at `x=0` and calls `set_selectable(false)` (`crates/clave-bar/src/main.rs:441`), so a tab's viewport BEGINS at the bar's right edge, and every floating percent is a percent of the reduced area. `#110` was raised — and half-designed — believing an explicit `x` past the bar was needed to keep it visible; Ollie disproved it live, resizing a floating pane with `Alt n` `+` until it stopped and never reaching the bar. Note the qualifier: a plugin pane is selectable by default (`zellij-server/src/panes/plugin_pane.rs:136`); it is the plugin's own `set_selectable(false)` call, not `borderless=true`, that does this.
- **The two floating-geometry paths clamp overflow DIFFERENTLY — one shrinks the pane, the other slides it out from under you.** A `Run { floating true; … }` keybind lands in `adjust_coordinates`, which floors `x` at `viewport.x` and then *narrows* the pane to the viewport's right edge (`zellij-utils/src/pane_size.rs:291-321`) — safe. A floating pane declared in a **layout** lands in `position_floating_pane_layout`, which compares against `viewport.cols` having dropped `viewport.x`, and on overflow *decrements `x`* (`zellij-server/src/panes/floating_panes/mod.rs:320-323`) — so an oversized layout pane walks left over anything the viewport offset was protecting. Don't carry a geometry from one path to the other without re-checking it.
- **zellij RECYCLES tab ids** — `get_new_tab_id` is `self.tabs.keys().last() + 1` over a `BTreeMap` (`zellij-server/src/screen.rs:1617`), so closing the *highest*-id tab hands that id to the next tab created. Makes bind/timeline pruning correctness-critical, not hygiene.
- **`children` must be a DIRECT child of `default_tab_template`.** Nesting it inside a wrapper pane *parses fine*, but the fill path `default_template()` inserts the default terminal pane only at the template's own top-level `external_children_index` and does not recurse (`zellij-utils/src/kdl/kdl_layout_parser.rs:1747-1761`, non-recursion enforced at `:1712`). Result: tabs with a bar and **no terminal**. Symptom in a dump: the wrapper keeps `external_children_index=Some(n)` forever.
- **`default_tab_template` wraps EXPLICIT `tab` nodes too** — so a `tab` node carrying its own bar pane renders TWO plugin instances in one tab: visibly wider, executor election scrambled, presenting as a dead Alt+c. Launch layouts must use a bare tab node and let the template's `children` slot take the terminal. (commit `5cb8b17`)
- **Layout sibling panes stack HORIZONTALLY (rows) by default** — `impl Default for SplitDirection = Horizontal` (`layout.rs:2065-2069`), and under Horizontal `size=N` binds to *rows* while cols is inherited (`:1947-1955`). `pane size=26` gives a 26-ROW top strip, not a left column. Fix: `split_direction="vertical"` on the parent.
- **Mixing bare top-level `pane` nodes with `tab` nodes is a parse error: `"Cannot have both tabs and panes in the same node"`** (`kdl_layout_parser.rs:2269/:2286/:2316`). `default_tab_template` plus bare top-level panes is fine.
- **A `MessagePlugin` block inside a `bind` needs a node terminator after its closing `}` — a newline or a `;`.** The multi-line form parses fine without one; the inline form `bind "Alt h" { MessagePlugin "…" { … } }` fails with `Expected valid node terminator.` (kdl 4.7.1). Zellij's own corpus writes `};`, which is why the `;` habit stuck. It fails at *session launch* — catch it with `zellij --config <cfg> setup --check`.
- **Zellij plugin permissions are ALL-OR-NOTHING per plugin** — a partial cache match raises an interactive prompt that is effectively unanswerable in a narrow bar pane, and withholds the *entire* set, so every `zellij pipe` times out with `Action CliPipe did not complete within 1s` and nothing renders. Pre-seed `permissions.kdl` under BOTH the `"file:<abs>.wasm"` and `"<abs>.wasm"` key forms. Read the current file rather than any doc for the exact set. (format: `zellij-utils/src/kdl/mod.rs:5456-5500`)
- **`EventType::InputReceived` carries no payload** — `EventType` is a strum discriminant enum over `Event` (`zellij-utils/src/data.rs:943`), so *every* variant is payload-free by construction. It cannot distinguish a nav keybind from a keystroke. Using it spawned one subprocess per keystroke and exhausted the server's file descriptors. EMFILE panic site: `zellij-utils/src/ipc.rs:388`, `try_clone_stream().unwrap()`.
- **[FIXED] Claude Code ROTATES its session id on `/clear` — a NEW id and a NEW transcript.** (`--resume` does NOT: measured 2026-07-31 on CLI v2.1.220, it continues the resumed transcript under that transcript's own id, so a resurrected pane keeps the id clave handed it.) — so any store keyed on the id clave minted at spawn silently orphans the moment the user clears. The hook then fires with an id matching no row, takes its untracked-session fast path, and the row stops stamping `last_interacted` forever: it never rises, never changes status, never rolls title/summary, while the tab is alive and fine. Measured 2026-07-31 on the maintainer's own daily-driver tab — **5.9 days stale while being typed into**. Invisible to every test, because fixtures use one uuid for the life of a row so rotation is not an input anywhere. Never join on the payload's `session_id` alone; the minted uuid travels in `CLAVE_AGENT_UUID`, and the CURRENT transcript is `payload.transcript_path`, never a path rebuilt from `rec.cwd` + uuid. Guarded on both halves. READ: `hook.rs::resolve_row` (the `CLAVE_AGENT_UUID` fallback) and `hook.rs::resolve_transcript`. RESURRECTION: the row remembers the live id in `AgentRecord::live_session`, and `spawn.rs::resume_target` execs `--resume <live>` when that transcript exists — because **`claude --resume <superseded-id>` does NOT re-chain lineage; it reopens that file and appends to it** (measured 2026-07-31: the resumed agent knew only the pre-`/clear` content, no third transcript was created). Everything that joins a session id back to a row must go through `live_session` too — `add.rs::resume_candidates` (jsonl stems), `add.rs::live_uuid_union` and `open.rs::open_is_live` (the `dump-layout` scan) all do, and without it a rotated session shows up as a stranger: an unattached resume candidate for a session already open in a tab, or a live pane the liveness fallback cannot see, which lets a commit (Alt+Enter, #100) open a SECOND tab on it. Note the last two are blind spots the resurrection fix CREATES — before it, a resurrected pane ran `--resume <minted>` and the scan saw the row's own uuid. (#97, #87, #99)
- **[FIXED] Env set before an `exec` into Claude is inherited by EVERY descendant, including nested `claude` processes** — so an env var saying "which agent am I" is ambient authority, not identity. A `claude` an agent shells out, or `clave dev`'s own `claude -p`, carries the parent's `CLAVE_AGENT_UUID`, and its session id is equally unknown to the store — so a membership-only check hands it the parent's row and it writes that row's status, ordering and prose. Gate on `CLAVE_AGENT_PID` vs Claude's own `CLAUDE_PID`: `exec` preserves the pid, so clave's `process::id()` IS the agent Claude's, and a nested `claude` re-exports its own (verified 2026-07-31 — a nested run reported its own pid, not its parent's). Fail CLOSED when either is missing. Guarded by `hook.rs::PidGate`, which `resolve_row` consults before ever taking the env fallback. (#97, caught in review before it shipped)
- **`zellij action` against an absent or dead session blocks INDEFINITELY and never errors** — an ungated `dump-layout` once hung `dev status` for minutes. Always gate on liveness first.
- **`dump-layout` MAY report a pane's MCP child instead of the agent process** — a sandbox tab running `clave spawn <uuid>` (which execs `claude`) dumped as `command="uv" args "--directory" "…/whatsapp-mcp-server" "run" "main.py"`, because Claude's MCP servers are children in that pane. It reads exactly like clave generated the wrong launch layout; `launch.kdl` was correct all along. Cost a round during the D28 gate-2 run. **Never identify an agent pane from `dump-layout`** — check `ps` for `claude --resume <uuid>`, or `clave dev status`. Also note `start_suspended true` appears on a pane that is running perfectly well.
- **`zellij action list-panes -t -j` reports a pane's DEEPEST CHILD, not the agent** — the same trap as the `dump-layout` entry above, confirmed on the live fleet: agent panes showed `rust-analyzer`, `uv … run spotify-mcp` and `caffeinate -i -t 300` (Claude's LSP, MCP servers and its keep-awake child) where `claude --resume <uuid>` was expected. Only tabs whose `pane_command` names `claude` are joinable to a uuid; the rest are **unknown, not mismatched**. Reading them as mismatches invents a mis-bind, and filtering them out silently hides a real one — print every pane and mark the unresolvable rows. (PR #120 live validation)
- **`go_to_tab(position+1)` is a silent no-op from a plugin** — a 0-/1-based mismatch, not a client-context problem (ruled out by driving it from a keybind). Use `focus_pane_with_id(PaneId::Terminal(id), false, false)`; zellij pulls the tab forward.
- **zellij live-watches `config.kdl` and hot-swaps keybinds into RUNNING sessions** (~1 s poll) — but the running bar keeps its load-time `initial_userspace_configuration`. So regenerating config against a live session re-keys its keybinds to an identity the on-screen bar does not have, and the next keypress starts a second bar. **Kill and relaunch every affected session after any `just release`, `clave setup`, or `clave dev scenario` that changes `clave_binary` or the wasm path.**
- **`zellij --config <path>` DISCARDS the user's `~/.config/zellij/config.kdl` entirely** — `Config::try_from` early-returns on `opts.config` and merges that file over zellij's *built-in defaults* only, never reaching the `find_default_config_dir()` branch (`zellij-utils/src/input/config.rs:170-186`). So every clave session replaces the user's keybinds, `default_mode`, `pane_frames` and `ui`. Themes are a partial exception — `apply_themes_to_config` still reads `~/.config/zellij/themes/` (`zellij-utils/src/setup.rs:318-341`) — and a terminal-level colourscheme masks the loss completely, which is why this went unseen for months. **If a user's zellij keybind behaves like stock zellij inside clave, that is this, not user error** — it cost #110 a misdiagnosis. (#122)
- **zellij resizes in ~5%-of-viewport steps** — "shrink while cols > 26" blew straight through the target (27→13). The seek is render-driven with an in-flight guard, a learned step clamped to `MAX_LEARNABLE_STEP = 20` (`clave-bar/src/model.rs:151`), and half-step acceptance. (C6 rounds 9, 16, 17, 20)
- **zellij's minimum-pane-width floor stops the collapse seek, and where it stops is window-dependent** — 14 cols on the dev window vs ~10 in the real session. "Wherever cols stop changing is accepted" is the ruling. (C8)
- **`move_pane_with_pane_id_in_direction` is a geometry SWAP** — the landing move hands the shrunk width to the terminal, so a width-then-move ordering races and pumps 75→30→75 on the fastest render chain. (C6 round 18)
- **zellij serializes the LIVE discovered pane process, not the baked layout command** — with MCP servers configured, `dump-layout` showed agent panes as `uv … run main.py`; an unreaped child once made every agent pane serialize as `command="<defunct>"`. Derive liveness from store binds, never from serialized command strings. (#6)
- **Every `zellij pipe` also delivers one empty EOF message per instance**, and logs `CliPipe did not complete within 1s timeout` plus `1000 consecutive unknown messages … logging client out` even with `unblock_cli_pipe_input`. Benign and pre-existing since v0.1.0 (#45) — but it buried the real evidence during the v0.1.1 incident. The keybind `MessagePlugin` path is clean.
- **"Nav is dead in the whole session, only `Alt+c` still works" is an ELECTION failure, and `dropped … pipe with empty payload` is not the evidence — it is a control that appears in the healthy state too (#162).** The payload arrives on every live instance (0.44.3 clones it per recipient and filters against the running set at delivery; the empty twin is the entry above), and then the executor election declines to act, so nothing runs and nothing is logged. The 2026-08-10 sighting read as pipe starvation for exactly this reason and was diagnosed as one for a day. Discriminator: a keybind `clave-nav` press that produces NO focus change and NO log line at all means the payload landed and the gate refused. Root cause that time: the beacon named a tab that had closed, and the re-anchor that should have re-seeded it cleared its own trigger even on the frames where it could not send.
- **Each of those 1s CliPipe timeouts BLOCKS the server router — N concurrent `zellij pipe` subprocesses are ~N seconds of frozen keyboard input.** One pipe per user gesture goes unnoticed; the resurrected organic announce fired one per bar instance and froze nav ~2s per `Alt+o` (measured live, #128 2026-08-02). Any announce a broadcast pipe or a toggle-burst TabUpdate can trigger MUST be gated to one emitting instance (`ReanchorVisit` pattern) — never "self-clearing per instance" alone; self-clearing bounds repeats, not fan-out. And put that gate at EMIT time, in the model, consuming the trigger only on the branch that emits: a gate in `run_effects` over a trigger the model already cleared is #162.
- **`zellij pipe --name X` with no `--` payload STREAMS stdin — and a killed client wedges the session's whole CLI-pipe lane.** The client blocks reading stdin; killing it (a script timeout will) leaves the server holding the half-open stream, and every later `zellij pipe` queues behind it indefinitely while `zellij action` keeps working — reads exactly like the bar stopped unblocking pipes. **An empty-string payload (`-- ''`) counts as absent and streams too** — it re-bit the same driver three days later. The wedge is CUMULATIVE: each killed client degrades the lane further (seconds → minutes per pipe). No recovery found short of relaunching the session. Payloads must be explicit AND non-empty; a hung pipe client must be un-hung by feeding its stdin an EOF, never killed. (#128 drive, 2026-08-01/04)
- **A `clave-status` hook push can spin FOREVER against a live session** — `hook.rs:399` runs `zellij pipe` with no timeout; one lost unblock left an orphaned client spinning for two days at full core against the maintainer's fleet, hammering its router with `unknown message` storms and 1s `CliPipe` stalls (found 2026-08-04, killed at 3155 CPU-minutes). The hook's own timeout reaps the hook, not the grandchild. Until the push is bounded, a laggy fleet warrants `ps aux | grep 'zellij pipe'` before deeper debugging.
- **`zellij --session <name> --layout <f>` means "add tabs to the EXISTING session"** and errors if absent. A new named session from a layout is `zellij -s <name> -n <layout>` (`zellij-utils/src/cli.rs:56-71`).
- **`CommandChanged` is a 1 Hz argv-change-gated sampler, and `is_foreground` means "the pane's direct child has a child"** — so its `true` transition is exactly command-*start* and never command-completion. Sub-second commands fall inside one poll window.
- **`Ctrl+D` in an agent pane does NOT close the tab** — panes run `clave spawn` (idempotent resurrect), so zellij holds the pane and re-runs it. `Alt+w` is the close path. (The stale `Ctrl+D` premises in `model.rs`'s re-anchor comment and its test were corrected with #162.)
- **The zellij log is shared by EVERY session on the machine and old entries linger** — `$TMPDIR/zellij-<uid>/zellij-log/zellij.log` (macOS: under the OS temp dir, **not** `~/Library/Caches`, which holds `permissions.kdl` instead). A date filter is not enough: on a same-day cut it returns the previous version's loads too. Mark the line count before launching and read only what was appended.

## PATH and version coherence

The family of bugs that shipped v0.1.1 broken. See CONTRIBUTING "The one leak".

- **[FIXED] `clave-bar` used to shell out to bare `clave` through `PATH`** in 7 places while `config.kdl` baked the versioned path for keybinds only — so on 2026-07-22 a stale `0.1.0` binary served `clave open` inside a `v0.1.1` session and composed layouts pointing at the *old* wasm: two plugin populations, duplicate sidebar, dead nav. The CLI now arrives as the `clave_binary` plugin-config key (`clave-bar/src/plugin_config.rs:21`, `main.rs:371`), guarded by a literal-count test. **Do not reintroduce a PATH lookup.** (#43/#44, fixed in #66)
- **`just dev-install` rebuilds the SANDBOX wasm in place, so it is unsafe against a live `clave-test` session** — that is the remaining hazard, and it is the reason `just sandbox` (which refuses while `clave-test` is alive) is the reviewed path. It no longer touches the daily binary: since #43b it installs `~/.cargo/bin/clave-dev`, and since #43a the release owns an unversioned launcher at `~/.local/share/clave/bin/clave`. **[FIXED]** Before #43b it wrote `~/.cargo/bin/clave` — the name the daily surface answers to — which is how a working-tree build could take over the fleet. Do not reintroduce that name. If a pre-#43b `~/.cargo/bin/clave` survives on a machine it shadows the launcher: identify it (`command -v clave; clave --version`) before removing it.
- **`just dev-install` leaves the sandbox's `config.kdl` STALE** — it installs the wasm and CLI but never regenerates the sandbox config; only `dev scenario` calls `run_setup`. So `dev-install` then `dev launch` pairs a new `launch.kdl` with an old `config.kdl`, every keybind misses, and a second bar spawns — indistinguishable from "the fix didn't work". It produced a false negative during #44's own live validation. **`just sandbox` is the only path that yields a coherent sandbox.** (#31, open)
- **A keybind `MessagePlugin` with no `payload` attribute delivers `payload = None` — so a pipe arm in the payload-present match is UNREACHABLE for it.** `clave-organic` sat dead exactly there: the empty-payload guard special-cased only `clave-toggle` and logged-and-dropped everything else, so the Alt+o beacon never announced, the departed bar's `current_tab` (and any dormant selection) went stale forever, and #100's commit opened an 18-seconds-old selection while looking like a photo-finish race. A payload-less pipe must be handled in the `else` branch, by name, next to toggle. Found live because the unit test called the model directly and `main.rs` routes nothing under test. (#128, 2026-08-01)
- **[FIXED] The sandbox used to be a machine-wide singleton, and CONCURRENT agent sessions silently clobbered each other's staging** — two sessions each ran `just sandbox` for their own branch; the second's artifacts won, and the first's live checklist measured the wrong build for a full round: the old dwell "reproduced" and the new keybind "didn't work", both artifacts of someone else's wasm. Sharper still, `sandbox-setup.sh` copies the wasm *before* its live-session guard, so even a REFUSED rewire mutated `data/` — a mixed dir (this branch's wasm, that branch's `config.kdl`) was a reachable state. **The instance is now per working tree** (`crates/clave/src/sandbox.rs`): session name, state dir, data dir and shim dir all derive from ONE key, the worktree directory name, so `clave-test-prune-wt` at `~/.local/state/clave-dev-prune-wt` cannot read or write `clave-test-s112-seg`'s. The MAIN checkout deliberately keeps the bare `clave-test` / `~/.local/state/clave-dev` — that branch is `key_for` returning `None` on a path equal to the main worktree, and it is the one every other doc names. **Two residues survive and are not covered by this**: `just dev-install` still hardcodes `~/.local/state/clave-dev/data/clave-bar.wasm` (`justfile`), so running it from a worktree writes the MAIN sandbox — that is the remaining reason `just sandbox` is the reviewed path (#31); and the drive-loop discipline is unchanged, because a per-worktree root does not tell you which build LOADED — still never read a live result before drive-loop step 3: grep the zellij log for your own `build=<tag>`. (#100 validation, 2026-08-01; fixed 2026-08-07)
- **A sandbox root name is a PREFIX of every longer one, and munging is lossy — so `dev reset` nearly deleted every other agent's scenario transcripts.** Scenario uuids are deterministic (`00000000-…-c85c<n>`) and therefore byte-identical across instances, so the old "delete every `c85c-*.jsonl` under `~/.claude/projects`" sweep was machine-wide by construction; per-worktree roots made it worse rather than better, because `scripts/sandbox-setup.sh` runs `dev reset` on every staging run. The obvious narrowing — match project dirs against `munge_cwd(root)` as a prefix — does not work: `munge_cwd` maps every non-alphanumeric to `-` (`munge.rs`), so the main checkout's `…-clave-dev` is a prefix of a worktree's `…-clave-dev-wt-a`, and a worktree literally named `repos-x` re-collides in the other direction. `dev reset` now names the EXACT munged directories by walking its own `repos/` tree before wiping it (`dev.rs::scenario_project_dirs`). Cost: two resets in a row leak the second one's transcripts, which are inert and are reseeded by the next `dev scenario`.
- **`CLAVE_STATE_DIR` sandboxes the STORE, not the SESSION — a snapshot-pushing command run from inside a live clave session pipes the sandbox store's state into the LIVE bars.** An end-to-end `clave prune` test against a temp store, run from a pane inside the daily session, flashed a three-row fleet onto the real sidebar until the next hook event healed it (2026-08-06, #149's own validation). `push_snapshot` pipes into whatever zellij session the process is standing in; the store override does not change that. Strip the zellij env (`env -u ZELLIJ -u ZELLIJ_SESSION_NAME …`) or run e2e checks from a terminal outside the session.
- **`launch.kdl` is stale by design until a cold start, so never assert on it *before* a launch.** Only `launch_session` writes it (`setup.rs:718`); neither `just release` nor `clave dev scenario` does. Any pre-launch check that includes it fails closed on a healthy setup — this has bitten twice: the release runbook's version glob, and `sandbox-setup.sh`'s #44 identity check, which read a pre-#44 `launch.kdl` from six days earlier and refused to set up a perfectly good sandbox. Check the freshly generated pair (`config.kdl` ↔ `layout.kdl`) before launch; assert `launch.kdl` after.
- **`just release` never rewrites `launch.kdl`** — `write_generated` writes `config.kdl` and `layout.kdl` only (`setup.rs:414-416`); `clave` composes `launch.kdl` at cold start. A `*.kdl` glob in a coherence check therefore orders a STOP on every healthy upgrade.
- **A version count is blind to UNVERSIONED references** — a KDL holding one correct versioned path *plus* a bare `clave` still reports "exactly one version" and passes, while the bare reference loads a second independent singleton. Probe the three sites explicitly: `clave_binary "clave"`, `Run "clave"`, `file:…clave-bar.wasm`.
- **Relaunching the old binary is NOT a rollback** — `clave` *attaches* to a live session (`setup.rs:733` `zellij attach --create`), so nothing is re-read; and once that session is dead, `config.kdl` still names the failed version, because `needs_version_refresh` (`setup.rs:589-595`) returns false as soon as the old binary's own wasm exists. Regenerate explicitly: `clave-v<LAST-GOOD> setup`.
- **`clave doctor` cannot see `PATH`** — its skew check compares only its own version against installed artifacts (`doctor.rs:326-352`). It reports "no issues" during exactly the incident the release runbook is hunting. (#48, open)
- **`runtime_binary()` probes only for its OWN version's copy** and falls back to bare `clave` (`release.rs:96-105`), which diverges from `config.kdl`'s versioned path. No longer silent: `binary_resolution_is_anomalous` (`release.rs:79-91`) warns and names the repair.
- **[FIXED] `starts_with("clave-v")` also matches a foreign `clave-vault`/`clave-verify`** in `bin/`, firing the divergence warning with no real mismatch — and a warning that cries wolf trains the reader to ignore the one that matters. Both sites now require a digit after `clave-v` (`setup.rs:270`, `release.rs:88`).
- **`zellij action start-or-reload-plugin` without `-c clave_binary=…` does not reload — it starts a second bar.** The one live mutation an agent may perform would spawn the very bug it exists to verify, while appearing to succeed.
- **Diagnosis is one grep:** `grep 'clave-bar: loaded' "$TMPDIR"/zellij-*/zellij-log/zellij.log`. Every line must report the same version **and the same `build=` tag** — the tag distinguishes two builds of the same version (`release.rs:44-50`, `clave-bar/src/main.rs:362`). `build=dev` means an untagged local build.
- **Two agents `dev-install`ing from different worktrees silently swap `~/.cargo/bin/clave-dev` under each other** — last write wins and neither is told, so the `clave-dev` you are testing may be someone else's build. It has happened, back when the dev and daily binaries shared the name `clave`. **Two things have narrowed it since, and the entry used to overstate it:** #43b moved `dev-install` to `clave-dev`, so the daily launcher is no longer in the blast radius at all, and the install is a staged rename (`.clave-dev.$$.tmp` → `mv -f`, `justfile`), so a losing writer can no longer publish a half-written executable. The silent swap is what survives; corruption and daily-surface damage do not. (#31, #43b)
- **`just release` does NOT upgrade a running fleet's hooks — the agents alive at that moment keep firing the PREVIOUS binary.** `clave release` merges absolute, versioned commands into `~/.claude/settings.json` (`clave-v<NEW> hook <Event>`), but an already-running Claude does not pick them up. Observed on the v0.1.2 cut (2026-07-31): after `just release` at 17:32 a live agent was prompted, the store moved and its status changed — so hooks fire, the fleet is not dead — yet `atime` on `clave-v0.1.1` and on a stale `~/.cargo/bin/clave` both landed on the write, and `live_session` (a field only the new binary writes) stayed null on every row. Indicative rather than conclusive — `atime` has other readers — but it is the reading that fits. **The consequence is what matters: for the length of that window a live fleet runs the old code against the new store, so no "prompt each agent once to migrate" procedure can work, because the process doing the writing is the one that lacks the field.** The cold restart #44 already requires is the only thing that closes it. Do not write a warm-migration step into the runbook; one was written on this cut and cut again the same hour.

## Build, test, CI

- **A bare `cargo test` exits 0 while silently skipping every `clave-bar` test.** `default-members` excludes the wasm-only crate. Measured on this tree: `cargo test` = 140 passed, `cargo test --workspace` = 208 — **68 tests skipped, exit 0 either way**. `--workspace` is load-bearing on `test` *and* `clippy`.
- **`cargo fmt --all --check` is a CI gate and runs BEFORE clippy** — hand-edited Rust can be clippy-clean and still fail the build. `just gates` runs all four in CI's order. **But `lint` is not a required status check** — branch protection requires only `["test","wasm-build"]`, so a red fmt/clippy does not block a merge. (#68, open)
- **`crates/clave-bar` sets `[[bin]] test = false`** — tests placed in `main.rs` compile and then *silently never execute*. `main.rs` is ~598 lines containing **zero** `#[test]`; all clave-bar tests live in `model.rs`/`plugin_config.rs`, reached via `[lib]`. Anything in `main.rs` — all effect dispatch and event adaptation — is unreachable by any test.
- **[FIXED] clap-derive turns a bare `bool` positional into a FLAG (`SetTrue`)** — `clave collapse true` could never parse, and clap's own diagnostic `debug_assert` fires *only in debug builds*. Fixed with `#[arg(action = clap::ArgAction::Set)]` (`clave/src/main.rs:144`) plus a parse pin. Every new CLI surface needs one.
- **`debug_assert!` is compiled out of `--release`** — the only build a release cut ever uses. An assertion written that way asserts nothing where it matters. Use `anyhow::ensure!`.
- **A KDL string that *contains* the right substrings can still be structurally invalid**, and it fails at *session launch* — the worst place, because a dead `attach` blocks forever and the human sees nothing. `crates/clave/tests/kdl_guardrail.rs` parses every generated artifact with the real parser, pinned `zellij-utils = "=0.44.3"`, `kdl = "=4.7.1"`.
- **`keybinds.0` is a `HashMap`, so comparing every layout config against an arbitrary `kb[0]` is order-unstable** — an extra key on one keybind broke plugin identity just as fatally as a missing one, but a `kb[0]`-only comparison escaped **9 times in 40 runs**. Assert all entries agree with each other *before* using one as the value.
- **A source-text guard asserting the ABSENCE of a literal is near-theatre** — asserting `"clave",` is absent survived three live mutations (a byte-exact revert, variable indirection, and disabling the feature outright), all passing the full gate set. **COUNT the literal instead** (`clave-bar/src/plugin_config.rs:90`).
- **`cargo … | tail` reports tail's exit status, not cargo's** — a failed gate recorded as a pass. Set `pipefail`.
- **…and with `pipefail` set, `cargo test | grep -q PATTERN` reports CARGO's exit status, not grep's** — the same trap in the mirror, and it is the more dangerous half because it fires in the harness you built to *check* something. `cargo test` exits 101 on a test failure, so `if cargo test … | grep -q 'test result: FAILED'; then` takes the ELSE branch on every real failure: a red-first harness reported **18 of 18 deliberately reinstated defects as "the test cannot fail"**, which reads as a damning finding rather than a broken script. The second attempt at it then classified every genuine RED as "does not compile", because `error: test failed, to rerun pass -p clave --lib` is what cargo prints for a TEST failure and the detector grepped `^error`. **Capture the output first (`out="$(cargo test … 2>&1)"`), then grep the variable; detect "did not build" by the ABSENCE of a `test result:` line, never by the presence of `error`.** (2026-08-07, the sandbox-segregation red-first run)
- **[FIXED] A cargo-dist *fragment* under `.github/workflows/` gets executed by GitHub** — `build-wasm-setup.yml` failed on every push, normalising red CI. Moved to `.github/` by #67. **cargo-dist regenerates it, so re-check the path after every dist upgrade.**
- **A blanket untracked-file exemption in the release gate is unsound** — tracked code can reference an untracked file (`mod foo;` with `foo.rs` never added): it builds locally but the tagged HEAD cannot reproduce it. Allowlisted to `docs/`, `.claude/`, `AGENTS.md` (`release.rs:161`).
- **[DISCHARGED, and it recurs] A mechanical search-and-replace of a width constant silently breaks a test.** When `BAR_TARGET_COLS` went 30 → 44 and `COLLAPSED_TARGET_COLS` 4 → 30, **sixteen** seek tests went red, and **two** were found to have stayed green while asserting nothing — `30` had been both the old target and an arbitrary "far from target" start width, and it is now the *collapsed* target, so a width that used to prove a shrink now proves a settle. **That sweep was not exhaustive**: two later reviews each found another shape it had missed. Four shapes to look for, all live: a start width that is now ON a target (converges in zero steps, asserts nothing); a landing whose delta no longer brackets the target (`seek_waits_for_inflight_resizes_and_zellijs_floor`'s floor loop turns from a near-target wall into a clobber re-drive); a test that stays green and stays *meaningful* while quietly covering **less** (`harness_newborn_converges_on_the_template_from_above` started at 60 and drove two resizes against 30, but only one against 44, so it stopped exercising the post-learning band; the fix was to pick a start width that still forces two); and — the worst of the four — **a test whose name and comment claim a property it does not prove, sitting exactly where the next agent looks to confirm the bug is impossible.** `the_two_targets_are_separated_by_more_than_the_widest_acceptance_band` asserted `2*sep > MAX_LEARNABLE_STEP` under the comment *"the bands are also disjoint"*; that is algebraically the same statement as `sep > 10` three lines above it, and it proves only that neither *target* sits in the other's band — never that no *width* does, which is the property Alt+c depends on and the one 44/30 had already lost (LEDGER D21). Green, meaningful, and misleading. The real property is now driven through `width_seek` itself (`no_width_is_accepted_for_both_targets`) rather than restated as algebra. **Re-derive every width from the new targets; do not substitute numbers until the suite goes quiet — check the tests that stayed green for lost coverage, not just for vacuity, and re-read what each surviving assertion actually says.** (#63, #86)
- **`cargo mutants` obeys `default-members` TWICE, and both silences look like success.** Generation: `cargo mutants --file crates/clave-bar/src/render.rs --list` prints **0 mutants and exits 0**; with `--workspace` it prints **81**. ## The bar's model — frame joins, latches, ordering

Read this section before touching `clave-bar/src/model.rs`. Every entry here is
a live defect or a live constraint, and S0–S8 all land in this file.

- **[FIXED — the join remains, guarded] `is_active_instance()` and `own_tab_id()` joined two independently delivered zellij frames BY TAB POSITION** — the last `PaneUpdate`'s `plugin_panes` against the last `TabUpdate`'s `last_tabs` (both joins lived in `clave-bar/src/main.rs` and are GONE — identity now resolves in `model.rs`, `own_tab()`/`elects_confirmed()`/`elects_presumed()`). A tab close renumbers positions, so in the window between the two frames the join silently returns a **different tab's** identity: the wrong bar elects itself, binds its agent to someone else's tab, and `apply_bind` evicts the rightful tenant (`store.rs:302-315`, "Evict any OTHER agent still bound to this tab_id"; that branch now logs `bind-evict`, which is the direct detector). Two separately reported symptoms are this one defect. **The join cannot be eliminated** — nothing in zellij-tile 0.44.3 hands a plugin its own tab identity (`PluginIds` has no tab, `PaneInfo` has no tab, `get_focused_pane_info` answers for the whole client, `get_tab_info` inverts the wrong way), so position is the only cross-frame key the two events share. It is now **witnessed**: `frames_coherent()` compares the manifest's tab-position key set against the tab set's, and `own_tab()` returns `None` while they differ — the caller does nothing and the next frame is the retry. Identity moved into `model.rs` because `main.rs` is `test = false`, which is *why* this shipped. **Residual, by construction:** a position-*preserving* permutation (close the lowest tab, create one in the same window) satisfies the witness; the self-healing bind below downgrades that from permanent to one transient mis-bind. (S0/#55)
- **[FIXED] `sent_binds` was a permanent latch** — inserted at emit, never removed, never cleared, not reset by `apply_snapshot`. A wrong bind could never be corrected for the life of the plugin instance. Replaced by `bind_sent` (uuid → target, `at_seq`, `tries`): re-emission requires the store's **`seq`** to have strictly advanced since our own send, capped at `BIND_MAX_TRIES`. **Do not re-gate this on the pipe echo** — that is the C5 round-4 shape that re-fired per TabUpdate and exhausted the zellij server's fds. `seq` advances only on a real store mutation, so a quiescent store costs zero subprocesses however many frames arrive.
- **`birth_touched` latches on the tab ID, and zellij recycles ids** — close the highest-id tab, press `Alt+t`, and the new tab is *permanently* unstamped → sort key falls to `unwrap_or(0)` → below every dormant row (`model.rs:354` the latch, `:559` `needs_birth_touch`, `:567` `sort_key`). Deterministic; no race required, so it likely fires more often than the races do.
- **[FIXED] `fire_binds()` was called after TabUpdate, PaneUpdate, `clave-status` and `clave-register` — but NOT after the hydrate snapshot** (the `Event::RunCommandResult` arm), which is the only thing that populates `self.agents` at session birth. So the eager cold-start tab was frequently never bound at all, and `bind_effects` looped empty `agents` for zero iterations, silently. The class — four call sites that each had to *remember* a second call — is closed by one entry point, `identity_effects()`, called from every arm that takes external input, with both snapshot paths folded into `apply_snapshot_and_settle`. The birth touch moved in with it (`Effect::Touch`), which is also how it gained a retry trigger: it used to live only in the TabUpdate arm, and a close delivers exactly one TabUpdate — the one where the frames disagree.
- **A full-live-set prune payload is order-unsafe across processes** — two fire-and-forget `clave prune-tabs` subprocesses have no arrival order, so a "retain only these live ids" payload landing after a new tab's bind unbinds a **live** agent, and the `sent_binds` latch means it never re-fires. The payload carries observed-**stale** ids instead: idempotent and commuting (`model.rs:665-712`).
- **Prune emission must NOT be set-change-gated** — a close `TabUpdate` arriving before its `PaneUpdate` leaves `is_active_instance()` false, silently dropping the effect, and a set-change gate then never retries. Emission is detection-driven, self-limiting via the store echo; `last_live_ids` was deleted (`model.rs:675-694`).
- **`ShrinkSelf` does not reliably make the bar NARROWER — `resize_pane_with_id(Decrease, Right)` resolves against whatever neighbour the live layout puts on that edge**, so its sense is a property of the layout, not of the effect. Measured 2026-08-07: the *same* plugin instance in the *same* session had it both ways — one episode walked 79 → 72 → 65 on `ShrinkSelf`, an earlier one walked 65 → 72 → 79 → … → 117 on the identical effect, climbing until zellij refused and then burning its whole budget hammering the wall. The maintainer's screen showed the bar at ~90% of the terminal. **Never assume the sign; the seek learns it from the observed delta**, the same way round 9 taught it to learn the step magnitude. Only the VISIBLE bar has enough render feedback to travel far, so this hides from any summary that reads hidden instances. (#137 round 2)
- **A trace of what the model BELIEVES its width is, is not pane truth** — the #137 round-1 validation read the instrumented `cols` per instance, saw 50 against a target of 54, and reported convergence while the bar was eating 90% of the screen. Only instances that render appear in such a trace at all. `dump-layout` is no help either: it normalises every pane to `size="33%"`/`67%` regardless of live geometry, and `dump-screen` returns **nothing** for plugin panes. The drive loop's "join against pane truth" step exists for this; a screenshot from the maintainer is currently the most reliable width oracle there is.
- **A runaway seek passes every "did it converge" assertion** — it terminates with its budget spent, and "budget spent mid-travel" is an accepted terminal state, so the width property greened on a bar that had walked 31 steps in the wrong direction. The assertion that catches it is about the JOURNEY, not the endpoint: the seek must never drive the pane further from its target more than twice in a row (one overshoot, one beat of latency). Check any new seek assertion against a *reinstated* wrong-direction defect before trusting it.
- **The seek's own-resize acceptance test uses distance, not provenance, so a SLOW external reflow is indistinguishable from our own resize landing** — a mover that shifts the pane one learned step per render satisfies `|cols − seek_last_cols| <= step` on every render, so the seek settles, one step at a time, all the way off target. Observed live 2026-08-07 with the seek emitting nothing at all while `cols` walked 42 → 35 → 27 against a target of 54 (#153, and the mover D37 still records as unaccounted). A fresh anchor does not save you here — the entry below is about a *stale* one, and this is the same test failing for the opposite reason.
- **`seek_last_cols` measured against a mid-flight *emit* anchor instead of the accepted rest width parks the bar off-target** — reproduced exactly as 30→16→6, then an external 26. `settle_at()` is the single settle helper and must pin the anchor at every settle path (`model.rs:978-992`). Pure logic inside a covered tier: the sim harness existed, the proptest never generated that interrupt shape. (#4/PR #27)
- **Two rapid `clave collapse` writes have no arrival order** — the change-gate swallows the correct write and the store pushes stale truth, *stickily*. Guarded by a pending-write ledger, `pending_collapse` + `collapse_reasserted`. **The ledger's first form was itself a storm engine (#137):** it re-asserted user truth on every contradicting snapshot and `toggle` reset that once-only budget on every press, so ten presses drove ~26 store writes — each write broadcasting another snapshot that contradicted newer local state. What bounds the writes now is that a contradicting snapshot is **inert**: while a write is owed it neither flips the mode nor buys anything, so the amplification loop has nothing to feed on. The re-assert stays once per **press** — rationing it once per *burst* was tried on PR #152 and withdrawn, because the outstanding debt was the only available burst boundary and an unresolved debt never clears: one burst that ended with the store holding the wrong value made every later press part of that dead burst, and the bar could then never write the correction.
- **"ON CHANGE ONLY" is not a storm defence when the input is a backlog** — `heal_collapse` guarded its seek re-arm on the mode actually changing, with a comment citing round 11's perpetual-seek storm, and it stormed anyway (#137). Under a snapshot backlog *every* snapshot is a change, so the guard is what **sustains** the flip-flop rather than what stops it. Before trusting a change-gate, ask what happens when the thing you compare against is systematically stale, not just occasionally different.
- **A replicated display mode whose two writers have different latencies will flip-flop under a burst** — the local press is immediate on all twelve instances, the store snapshot is a round-trip behind, and nothing in the snapshot says "I am older than your intent". A value comparison cannot express ordering. Either the local intent wins until confirmed (what #137 chose) or the channel has to carry a version; a change-gate on the value alone is neither.
- **A sim harness less patient than the model measures a state the real bar passes straight through** — the width-seek harness declared the bar settled after 2 silent renders while the model needs 3 to decide whether to resume an incomplete rest, so every seek property was asserting about a transient (#137). Tie the harness's quiescence threshold to the model's own constant, never to a hand-picked number.
- **`now_unix()` stamps whole seconds and ties resolve on `tab.position` ascending** — two prompts 300 ms apart inside one wall second give the lower-positioned tab the win regardless of who was actually touched last (`store.rs:352-357`; sort at `model.rs:791`). The ordering key silently swallows a prompt.

## Claude transcripts — what the jsonl actually contains

The transcript tree is `~/.claude/projects/<munged-cwd>/<uuid>.jsonl`. Read it,
do not assume it: its line types changed under us once already.

- **`{"type":"summary"}` is EXTINCT — the label tier that has never once fired.** `summary_from_tail` (`hook.rs:116`) scans for it; Claude Code no longer writes it. Measured 2026-07-28: **0 of 919** local transcripts contain one, and all 14 live store rows read `label_source: first_prompt`, so every label is a truncated first-prompt fragment. Any test asserting `Summary`-tier behaviour is asserting against a hand-written fixture, not reality — re-point those at `ai-title`, do not delete them. Detect: `grep -rl '"type":"summary"' --include='*.jsonl' ~/.claude/projects | wc -l`. Re-measured 2026-07-29: still **0 of 153**. Re-measured 2026-07-31: still **0 of 770**. `rec.summary` and `rec.title` are now sourced from `ai-title` / `custom-title`; the LABEL tier is still pointed at the extinct line and so still never fires — retargeting it is S4's call, not a bug that appeared. (#79)
- **The signals that DO exist:** `custom-title` (the session's **set title** — a rename IS one of its writers: re-measured 2026-08-01 against sessions with known renames, the values are exactly the names given (`CLV-MAIN`, `#118`, `N-CHEK`), not first-line derivations. The 2026-07-31 "written from a session's first line, no rename involved" reading mistook titles *seeded from the first prompt by whatever surface opened the session* for a derivation rule; treat the record as "this session's title, whoever set it" — that half was right. Once set, it re-stamps every few turns, single-valued), **`ai-title`** (Claude's auto-description — the real replacement for `summary`), `last-prompt`, `worktree-state` (carries `worktreePath`, `worktreeName`, `worktreeBranch` — provenance with no git call), `relocated`, `agent-name`. Inventory them before designing a tier: `grep -ho '"type":"[a-z-]*"' ~/.claude/projects/*/*.jsonl | sort | uniq -c | sort -rn`.
- **`ai-title` is NOT rolling — it is re-stamped, unchanged, for the life of the session.** Every spec calls it "Claude's *rolling* auto-description" and reasons about it upgrading turn by turn. Measured 2026-07-29 over 153 local transcripts: 74 carry an `ai-title`, up to **85 lines in one file, and never more than ONE distinct value per session**. So `rec.summary` is effectively "Claude's one auto-title for this session", not a live description of the current turn. The write path is still correct (last-non-empty-wins, no-op when unchanged); what is wrong is any *design* that assumes the summary column narrates progress. Re-measure before building on it: `grep -h '"type":"ai-title"' <file> | sort -u | wc -l`. **Presence has since collapsed, and the 74-of-153 figure above must not be carried forward:** re-measured 2026-07-31 over all 770 local transcripts, only 68 carry an `ai-title` at all, and restricted to the 389 with ≥20 user turns it is 45 — falling to **7 of 132** for substantive sessions in the preceding 7 days. Any design that assumes `rec.summary` is usually populated is designing against a field most rows will never earn (#111). **The collapse is now explained (2026-08-01, measured on #111): `ai-title` is generated ONCE, at a session-open where no title is set yet, then re-appended verbatim in each subsequent open's metadata cluster** — one transcript carries 28 reopen clusters and zero `ai-title` because its `custom-title` landed at line 18. Fleet-born sessions are titled at/near birth, so they never earn one; the collapse dates to clave becoming the daily driver, not to a Claude Code change. For any renamed-at-birth row, the prompt-derived fallback is the summary's permanent real path. (#79, ux task 4)
- **A transcript RELOCATES when the session's cwd changes.** Claude moves the whole `.jsonl` into a project directory keyed on the NEW cwd, carrying its full history, and logs a `relocated` line. So any cwd frozen as a "stable transcript anchor" goes stale and the tail read silently stops returning anything — no error, just a row that never updates again. **S4 §3.2 asserts the opposite (*"never moves it"*) and is wrong.** Use `payload.transcript_path`, which every hook event carries. ## Rust and codebase specifics

- **`kdl` 4.7.1's `KdlDocument::get` returns the FIRST match only** (`kdl-4.7.1/src/document.rs:80`) — so a second `unbind` node in the generated config is silently ignored. All five unbound keys must ride one node, pinned by a `count == 1` test (`setup.rs:145-149`, `:948-966`).
- **The store lock must be a SEPARATE lockfile, never the data file** — the atomic rename swaps the data file's inode out from under a second writer's lock, and concurrent hooks silently lose updates. `agents.lock` is never renamed, so its inode is a stable anchor (`store.rs:2-9`, `:115`, `:147-148`).
- **`munge_cwd` must be fed the CANONICAL cwd** — Claude munges the physical `getcwd()` (macOS `/var`→`/private/var`, `/tmp`→`/private/tmp`), so callers must canonicalize *before* munging or the join key misses the jsonl and `clave spawn` hits `Session ID … is already in use` (`munge.rs:7-14`, enforced at `main.rs:219-221`).
- **[FIXED] `claude --session-id <uuid>` CREATES a session and refuses reuse against an existing jsonl** — which broke deterministic scenario seeding permanently after its first success. Now resume-or-create: an existing jsonl is the goal state, not an error (`dev.rs:208` `seed_needed`). Do not reintroduce unconditional seeding.
- **Backslash is KDL's escape introducer, and it passed every early guard** — a raw `\` in a baked cwd or a label (a prompt like `fix the \d regex`) is a layout parse error that can brick cold start through `launch.kdl`. `sanitize_label` filters `"` and `\` (`add.rs:80-93`); `validate_cwd` *rejects* rather than munges (`add.rs:152-159`), because a mangled path points nowhere and `clave spawn` would then canonicalize-fail on the lie.
- **`git rev-parse --show-toplevel` inside a LINKED worktree returns the worktree's own root** — inverting every `(wt)` marker and missing every store row keyed by the real root. Take the main tree from `git worktree list` entry 0 (`main_worktree_path`, `add.rs:211-213`).
- **Re-recording a resumed agent must NOT clobber its store row** — the row's `cwd` was canonicalized at creation and is worktree-aware; replacing it with the picked dir silently relocates a worktree agent to the repo root, bakes the wrong `--cwd`, and makes `clave spawn` miss the worktree-keyed jsonl and CREATE a fresh session. `merge_resume_record` resets only `status`/`tab_id` (`add.rs:335-360`).
- **`tab_position_of_pane()` must filter `!p.is_plugin`** — terminal and plugin pane-id spaces are different, so a plugin pane can shadow a terminal id (`clave-bar/src/model.rs:396-401`; `PaneMeta.is_plugin` populated at `main.rs:489-496`).
- **`register_plugin!` supplies its own `main` on zellij-tile 0.44** — adding an explicit `fn main()` to `clave-bar` is `E0428` (`clave-bar/src/main.rs:50`, `:597-598`).
- **`DefaultHasher` is not stable across toolchains** — anything hash-derived and user-visible (repo colours) would reshuffle on a `rustc` upgrade. Use store-backed iterate-and-wrap allocation instead. Standing constraint, currently unviolated.
- **Harness-injected text reaches `UserPromptSubmit` and would earn a permanent label** — resuming a session that died with pending background work makes the harness auto-fire a turn whose "prompt" is an orphaned tag. Earned labels stick, with no self-heal, so one leak bakes it forever. The guard matches the START of the trimmed string against `HARNESS_INJECTED_PREFIXES` and deliberately **never strips-and-uses the remainder** (`hook.rs:71-95`). (#17)
- **`CLAVE_*_BIN` overrides are deliberately NOT existence-checked** — a broken override must fail loudly at exec rather than be silently ignored. Do not "fix" this (`discover.rs:64-72`).
- **Use `which::which_global`, not `which`** — plain `which` lets the *cwd* satisfy a probe. A readable-but-not-executable file is not a hit either (`discover.rs:162-174`).
- **An OLDER `clave` binary writing the store SILENTLY STRIPS fields it does not know.** `with_store_mut` is read-modify-**write**: serde drops unknown keys on deserialize, so the whole row is re-serialized without them. **This entry predicted the moment `title`/`summary` became earned state and stopped being harmless; that moment is `0ccf04d` (#86), and the FOOTGUNS sweep at `94e0fa3` missed this line.** **The asymmetry this entry used to assert between `title` and `summary` DOES NOT EXIST — the cadence claim was measured and is wrong.** It said `ai-title` is re-stamped for the life of the session (so `summary` heals in a turn) while `custom-title` is appended "at rename, not per turn" (so a stripped `title` is permanently lost). Re-measured 2026-07-31 across all 770 local transcripts: **`custom-title` is re-stamped every few user turns, single-valued, from the moment it is first set** — 15 lines across 75 user turns, 71 across 280, 95 across 363. (The "written from the first line, no rename involved" reading of those numbers was corrected 2026-08-01: the value is the session's set title — seeded at open or renamed — not a first-line derivation; the cadence measurement stands.) `ai-title` behaves the same way where it appears. So a stripped `title` re-derives on the next `Stop`/`UserPromptSubmit` in every case measured, rather than being lost until the next `/rename`. **That is a measurement, NOT a guarantee, and the difference is the part to keep:** re-stamping is paced by turns and the tail window is 64 KiB of BYTES (`hook.rs:419`), so nothing structurally stops a turn that emits more than a window's worth of transcript from evicting the last source line before the next read. It has not happened here — across all 148 transcripts carrying either field the last occurrence sits inside the window, worst case 34,808 bytes of 65,536 — but a tool-output-heavy turn is the shape that would break it, and D25's eviction caveat is correct in principle even though the cadence reasoning attached to it was not. **The real limit today is PRESENCE, not cadence, and it is worse than the cadence story it replaces:** of 390 transcripts with ≥20 user turns, **297 carry neither field**; of the 93 that carry either, the two are near-mutually-exclusive (39 only `ai-title`, 48 only `custom-title`, 6 both). The last 7 days are worse, not better — 99 of 132 substantive sessions carry neither, and `ai-title` appears in just 7. That is a "the field is never earned in the first place" problem, not a strip problem, and which of the two a session gets is now explained (2026-08-01, on #111): `ai-title` generates once at a session-open with no title set — so named-at-birth sessions carry only `custom-title`, never-named ones only `ai-title`, and late-renamed ones both. **An `ai-title` therefore means "ran unnamed past its first open", NOT "never renamed"** (#111). **The visible cost is asymmetric, and only the chip goes blank:** `title` has no fallback tier, so an absent `custom-title` renders the blank chip D25 ratified; `summary` falls back through the extinct `summary` line to a first-prompt seed (`refresh_row_fields`, fill-only-when-empty), so a live row's summary is prompt-derived rather than empty — lower-quality, not missing. Do not read the absence numbers above as "most rows have no summary". Any field holding earned state needs either a version guard or a re-derivation path — and "it re-derives" must be checked against whether the SOURCE line is written **at all** in the sessions you care about, not merely how often. (#69 whole-branch review, #59, #86, #111)
- **A null `live_session` means TWO different things, and only one of them is a problem.** `apply_hook_event` holds the field at `None` whenever the reported id equals the minted uuid (`hook.rs:436`, `(live != uuid).then(...)`) — so null is the ordinary, healthy state of a row that never rotated, *and* the state of every row written by a binary predating the field. Nothing distinguishes them from outside. **The cost of misreading this is a bad migration:** on the v0.1.2 pre-flight, null on all 18 rows of the real store was read as "18 rows need backfilling" and became a P1, when the rows actually needing anything are only those `/clear`ed since their last resurrection — a set the store cannot name. Do not backfill by guessing (newest transcript in the project dir is the heuristic #99 exists to avoid: a project dir holds a transcript for every `claude` ever run there, and attaching the WRONG conversation is unrecoverable where a null merely falls back). The real fix is a versioned store schema that can tell "not yet migrated" from "agrees with the minted uuid" (#106). (#99)
- **[FIXED] `clave dev reset` must wipe only `["state", "repos"]`, never the sandbox root** — the old `remove_dir_all(root)` deleted `data/clave-bar.wasm`, a build artifact rather than scenario state, silently breaking the reset → scenario → launch loop with a rebuild demand. Test-pinned (`dev.rs:317`, `:418-424`).
- **[FIXED] Scenario worktree branches must NOT be tagged from the FRONT of `scenario_uuid`** — `add.rs:655`'s `&uuid[..8]` is fine on a real v4 uuid (effectively-random first 8 chars), but every `scenario_uuid` starts with the literal `00000000-`, so slicing the front 8 chars gives every scenario agent the SAME tag. Invisible until a scenario put two worktree agents in one repo (`ux-gate1`): `git worktree add -b clave/00000000` collided on the second one and failed closed. Tag from the TAIL instead (`dev.rs`'s `uuid_tag`, which is exactly the `{n:08}` suffix `scenario_uuid` mints) — any new scenario sharing a repo across 2+ worktree agents relies on this.

## Text, glyphs, rendering

- **Write every glyph as a `\u{...}` escape in source, never as a literal character.** Literal glyphs were silently lost in transit twice in one session; the first loss was misread as missing font coverage and nearly constrained the whole design to one Unicode plane. The failure mode is tofu in production from a diff that looked clean. **THE BAR IS NOW COMPLIANT; the host side is not.** #86 moved all visual logic into `render.rs`, which carries every glyph as an escape — so the sites this entry used to cite (`clave-bar/src/model.rs:771-775`, the truncation at `clave-bar/src/main.rs:583`) no longer exist, and "the 24 rendered sites are still literals" is no longer true of anything the sidebar draws. **What is still literal is all host-side:** `Status::glyph()` (`clave-types/src/lib.rs:58-62` — `'●'` ×4 and `'✖'`), which feeds `clave ls` via `lsview.rs:17` and which the bar deliberately does not use (LEDGER D10); its own test assertions (`lib.rs:435-439`); and the five label-composition sites that still spell `·` inline (`add.rs:384,858`, `hook.rs:283,292,308`) even though `LABEL_SEP` exists for exactly that. Test assertions duplicate the same literals, so a loss in both halves of one diff still passes green. (design lock §5.4, #40)
- **`·` U+00B7 is the label separator, and it is the highest-stakes literal in the codebase** — baked into every composed session label, therefore into every zellij tab name via `RenameTab`, and every bar row. Losing it in transit silently yields `x main fix auth`.
- **`✖` is U+2716 HEAVY MULTIPLICATION X, `✗` is U+2717 BALLOT X — different meanings.** U+2716 is `Status::Failed`, a hook-lifecycle status (`clave-types/src/lib.rs:41`). U+2717 is the *stale row* flag, a `bool` not a `Status` (`RowStatus::Stale` in `clave-bar/src/render.rs`, field at `clave-types/src/lib.rs:78`). Both render the same red, so shape is the only discriminator. **A third, unrelated use:** `clave doctor` uses `✗` for a failed check (`doctor.rs:404,415,482`) — a repo-wide replace would corrupt it.
- **[FIXED] The renderer used to build its gutter by string concatenation**, so a dropped or double-width glyph shifted the row's text, and `main.rs` is `test = false` so nothing caught it. `main.rs` now calls `render_rows` (`render.rs`) and holds no visual logic at all. **Keep it that way** — anything you add to `fn render` is untestable by construction.
- **`str::chars()` counts Unicode scalars, not terminal cells** — so an East-Asian wide or combining character miscounts the row. `render.rs` measures with `unicode-width` (held at 0.1 — the line zellij-utils 0.44.3 resolves for its own grid), and it is now **the bar's only clamp**: `main.rs`'s char-counting one is gone. The claim is scoped to the bar — host-side, `hook.rs:109` still does `chars().take(32)` on a composed label, and that one is a *store* budget, not a column budget.
- **A colour blend ported from the ratified preview must round ties to EVEN, not away from zero.** Python's `round()` is round-half-to-even and `f64::round` is not, so a naive port shifts a channel by one and the rendered design silently stops matching the one that was signed off. `Rgb::mix` uses `round_ties_even`; fujiWhite faded 25% onto sumiInk3 puts blue on exactly `149.5`, so this is reachable, not theoretical (`render.rs`, `mix_rounds_ties_to_even`).
- **[DESIGN] Below `min_intact_cols()` a rendered row is WIDER than the pane, deliberately.** Fixed columns everywhere with `summary` the only flex cell (LEDGER D9) means gutter + title + repo + spaces + margin + caps = 32 cells expanded (23 collapsed; it was 29 until #105 took the expanded battery cell to four columns, and 27 before D33 took `EXPANDED` to `(9, 7)` — derive it from `Widths`, never restate the number) that never shrink. A row that reflowed its columns to fit would be the failure lock §2.1 forbids, so the build never reflows — **it is a two-stage row.** `render_row` builds at `cols.max(min_intact_cols())`, over-running uniformly below the floor; `render_rows` then hands that over-run to `clip_to_cells`, because D13 assumed the terminal would clip it and the terminal **wraps** it instead — a blank second line under every row, observed live 2026-07-29. So a row is exactly `cols` cells at every width; what stays intact below the floor is the *uniformity*, not the width. Collapsed is ratified as a width PROFILE (LEDGER D16/D17), so the floor is `Widths::min_intact_cols()` — but the profile is chosen by STATE, not by width, so **nothing keeps the pane above the floor**: a tab spawned below ~123 columns is born under `EXPANDED`'s `min_intact_cols()` floor (32 as of #105). Do not "fix" this by shrinking a fixed column (`render.rs`, `Widths::min_intact_cols`, `clip_to_cells`). **As of #105 the collapsed resting width (30) sits BELOW the expanded floor (32)**, so every peek-on-nav and every Alt+c expand draws the EXPANDED profile through 30-31 cols on its way to 32 — a cosmetic one-frame blink (lost right margin, and for the selected row its right cap) during the grow animation, not a bug to chase.
- **[SUPERSEDED] `COLLAPSED_TARGET_COLS` is no longer `4`, the width the bar could never reach** — it is **30**, `Widths::COLLAPSED`'s own geometry (LEDGER D17), well above zellij's resize floor. Any collapsed-mode analysis costed against a "text budget 0" row was reasoning about a phantom and does not transfer.
- **[DESIGN] A `glyphs` plugin-config key would reproduce the v0.1.1 double-sidebar** — zellij hashes plugin identity over the whole config map, so a key miss starts a new instance. Glyphs are compiled in; customisation folds into #40. (lock §5.3)
- **[DESIGN] Gutter cells are position-locked and render a space when the glyph is absent; cap columns are reserved blank on unselected rows too.** Otherwise the selected row's content sits one column right of its neighbours — breaking alignment exactly where the eye is most focused. (lock §2.1, §2.2)
- **[DESIGN] A row background must span every column BETWEEN THE CAPS (`1..DESIGN_COLS-1`; the caps themselves are foreground glyphs), including the pad after a short summary** — resetting at end-of-text leaves a ragged selection, which is what the old `SGR 7` over the tab name did. Selection is by recession (25% fade), not by reverse video, and `a_selected_rows_background_spans_every_column` measures it per cell. (lock §6)
- **[DESIGN, now enforced] A live row renders from the STORE, not the zellij tab name** — a tab name is one opaque string with no field structure, so it cannot fill fixed-width columns. `rows()` projects title, summary, repo basename and provenance from the bound `&Agent`; the zellij tab name reaches the bar **only** through `RowContent::Terminal`, i.e. a tab with no agent. Reintroducing `t.name` on an agent row re-opens a second, drifting copy of the label. (lock §7.1)
- **`𖣂` U+168C2 is BAMUM LETTER PHASE-C MBERAE — not a Nerd Font glyph.** A working Nerd Font battery says nothing about its coverage; in practice only Noto Sans Bamum has it. There is no worktree glyph in any surveyed set: zero hits across Nerd Fonts' 10,764 names, 380 octicons, 639 codicons.
- **A mouse click carries a line of the VIEWPORT, not a row of the list — anything that maps clicks must offset by the same `viewport_top` the draw used.** The 2026-08-06 overflow had two symptoms, and the second one was the sneaky one: rows past the pane bottom were invisible, *and* clicks landed one or two rows above the row under the pointer, because `render` counted from row 0 while the screen showed a window starting further down. Fixing the picture alone would have looked like a complete fix and left the hit test drifting until the next overflow, so `render_rows` and `BarModel::click` read one function (`render.rs`, `viewport_top`) and the shell remembers the height at render because a `Mouse` event does not carry it. **`Alt+1..9` is the other convention on purpose:** a `{"row":N}` payload names a row of the FLEET and must NOT be offset — the jump brings its target on screen by moving the selection. (#148)
- **Two clamps that each make the other's mutants survive.** `viewport_top` originally capped the lookahead by the rows below the selection *and* clamped the top to the last screenful. Both are correct, the second subsumes the first, and with both present five arithmetic mutations inside the function survived the whole suite — every wrong answer was masked by the other guard. The suspicious signal is a survivor in a function whose behaviour you have goldens for; the fix is to delete the redundant guard, not to add a test for arithmetic that cannot be observed. (#148)
- **[DESIGN] The "this terminal renders Plane-15 only" rule was an encoding bug, not a font fact** — the probe's codepoints were lost between writing and running it. A corrected probe rendered every candidate, including U+E0A0. (lock §8.2)

## Process and tooling

- **Bare `zellij` commands from an agent shell mutate the maintainer's OWN session.** Claude Code runs *inside* the user's zellij session — `$ZELLIJ_SESSION_NAME` reflects that, not some sandbox. `zellij attach` variants once injected clave-layout tabs into the live session. **Session lifecycle is the human's; print the command, do not run it.** (docs/dev/TESTING.md)
- **The settings denylist on session teardown is a speed bump, not a boundary.** `.claude/settings.json` denies the exact spellings that would tear down the maintainer's `clave` session (`zellij kill-session clave`, the quoted forms, and the `*-all-sessions` nukes), added at his request after the 2026-08-07 incident. Bash deny rules match the command **text**, so a different spelling — a shell variable, an extra space, a name built at runtime — walks straight past them, and the rules deliberately do NOT cover `clave-test*` because tearing down your own sandbox is legitimate work. **And enumeration is the only option here, which is why the list looks the way it does:** the obvious tightening — deny the whole `zellij kill-session:*` prefix and allow the sandbox back — does not work, because deny beats allow, so it would block tearing down your own sandbox too (CodeRabbit found a missing single-quoted spelling on PR #164; the fix was to complete the quoting matrix, not to widen the prefix). Treat the denylist as the last of three guards, never the first: the real ones are structural — the per-worktree sandbox instance (#161) means you cannot *name* someone else's session by accident, and `scripts/ct.sh` refuses to run at all unless your own is provably live.
- **`ZELLIJ_SESSION_NAME=clave-test` is NOT a safety boundary — it is a preference, and it FAILS OPEN.** An agent shell inside the maintainer's session inherits `ZELLIJ=0` and `ZELLIJ_PANE_ID=<n>` as well as the session name. Override the name only, and while `clave-test` exists everything behaves; the moment it stops existing (another agent's `dev reset`, a crash, a kill you did not make) the CLI **falls back to the ambient session instead of erroring**, and every queued drive command lands on the daily fleet. That happened on 2026-08-07: a `start-or-reload-plugin` put a sandbox-built debug bar into the maintainer's live session as a real pane, and ten `clave-toggle` pipes went to his fleet. Nothing was corrupted — stable install, config and store all survived — but the session was visibly disrupted, and he found it before the agent did.
  **Preflight every drive, do not trust the variable** — or just use `scripts/ct.sh`, which is that preflight. It asserts the target's server socket exists, that a live server process holds it, and clears `ZELLIJ`/`ZELLIJ_PANE_ID` so there is no ambient session to fall back to; every command re-runs the guard, because the session can die mid-drive. Passing `--session <name>` to `zellij action` is itself a real guard and the env var is not: with a name supplied, `send_action_to_session` exits 1 when it names no live session, where with none supplied the `ActiveSession::One` arm serves the only live session whatever `ZELLIJ_SESSION_NAME` says (`src/commands.rs:407-452`, tag v0.44.3).
  **`$TMPDIR` carries a TRAILING SLASH on macOS and zellij's own paths do not**, so the obvious interpolation gives `…/T//zellij-<uid>/…` where the server's argv has `…/T/zellij-<uid>/…`. A `-S` file test folds the double slash and passes; anything matching argv as *text* — `pgrep -f`, a log grep — never matches. `ct.sh` shipped with exactly this and refused every command on every macOS machine while reading as "the sandbox is not running", i.e. it fails closed into looking correct. Normalise with `${TMPDIR%/}`, and glob `contract_version_*` rather than pinning `_1`. (found reviewing PR #152, 2026-08-10)
  **And treat a surprising instance count as a session-identity failure first.** The tell was there and got rationalised away: a reload reported ONE bar instance where twelve were expected, and "the reload created a new instance" is a much less likely explanation than "you are in the wrong session". Any drive reading that names fewer instances than there are tabs should stop and prove which session it is talking to.
- **Clave binds no close-pane key, so `Alt+x` does nothing** — the generated config is `clear-defaults=false` and unbinds exactly five stock keys (`Ctrl g`, `Ctrl t`, `Ctrl o`, `Ctrl b`, `Ctrl q`), adding only its own `Alt` namespace. Closing a pane is therefore stock zellij: **`Ctrl+p` then `x`**. Note `Alt w` is bound to **CloseTab** — reaching for it to remove a stray pane closes the whole agent tab. The real sidebar cannot be focused by clicking (`set_selectable(false)`), so a bar pane that *does* take a click is not the real one.
- **Hot-reload resets plugin state** — a reload reincarnates every bar model from scratch. That is a confound (the state you were watching is gone) *and* a tool (it clears a parity desync and re-hydrates cleanly). Know which one you are relying on.
- **Claude's identity is deliberately NOT sandboxed** — `CLAUDE_CONFIG_DIR` isolation broke auth (ruling 2026-07-18). So scenario seed transcripts land in the real `~/.claude/projects/`, and `~/.claude/settings.json` is one shared hook slot where Claude fires *all* matching hooks — clave keeps exactly one entry per event or they double-fire.
- **`~/.claude` is never yours to write.** Note sandbox task-output paths can *symlink* into `~/.claude/projects/`, so a write believed to be sandboxed can land in the real transcript store.
- **Handoffs and the validation ledger are IMMUTABLE history** — a doc sweep may correct live SOP only, never a dated record of what was run. A blanket "fix every occurrence" instruction once had an implementer falsify a dated quote, inserting a flag that did not exist on that date.
- **A branch updated via `gh pr update-branch` diverges from your local copy** — fetch and merge before pushing. Branch protection requires up-to-date-with-base, so merging PR N forces a branch update on PR N+1 and a fresh CI round. Direct push to `main` is blocked (`enforce_admins: true`); note approvals required is **0**, so "ask before merging" is unenforced.
- **Global git config rewrites HTTPS→SSH** (`url.git@github.com:.pushInsteadOf`), so a dead SSH agent blocks pushes as well as signing.
- **The fugu harness had a silently-passing lane** — its codex lane hardcoded `git diff <base>...HEAD` regardless of `type`, so reviewing UNCOMMITTED work diffed nothing and returned "nothing significant". Fixed in the vendored copy (`.claude/workflows/fugu-review.js:59-74`); a global copy outside this repo may still have it. **A review lane that can only ever agree is worse than no lane.**
- **Workflow `args` must be a real JSON object, not a stringified one** — a stringified value still passes the truthiness check and silently drops the object's fields (`fugu-review.js:55-57`).
- **Subagents are instructed not to write report files** — briefs must ask for the report as the final text response. Subagents also misread per-task constraints as standing project rules; one nearly encoded a session-specific restriction into a project doc.
- **A pre-commit PII blocklist rejects private local path names in staged lines** — genericize to `~/…`, `$TMPDIR/…` before staging, and keep the reason out of commit messages and PR bodies.
- **`~/.claude/projects/` entry names begin with `-`, so a RELATIVE glob over them parses as flags.** From inside the directory, `ls *clave*` expands to `-Users-…` and `ls` reads it as options: `ls: unrecognized option '--var-folders-…'`, exit 1. **The absolute form is fine** — `ls ~/.claude/projects/*clave*` expands to `/Users/…`, which no `ls` mistakes for a flag (measured: exit 0). Getting this backwards is worse than not knowing it, because the absolute form *succeeds* and reads as "there is no trap here". `ls` is also aliased to `eza`, where `-t` means `--time` and errors demanding a field. Canonical command: `find ~/.claude/projects -maxdepth 1 -name '*clave*'`; `/bin/ls --` also works. Cost a round during the #69 spike. (corrected on #81 — the original entry named the wrong failing form)
- **`just install` is retired.** It clobbered stable wasm and CLI from an in-progress working tree. `just sandbox` replaces it and guards three things: it refuses against a live `clave-test`, self-checks that `config.kdl` and `launch.kdl` carry an identical `clave_binary`, and asserts `~/.cargo/bin/clave` and `~/.local/share/clave` were left untouched.
