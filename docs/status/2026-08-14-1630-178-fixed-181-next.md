## Important Discoveries

### On #181 — the constraints that decide the design

- **The runaway is a REGRESSION in the 0.1.3 cycle**, per Ollie: not present in
  v0.1.2. Verified that the 54-column target is NOT the cause — it predates
  v0.1.2. Prime suspect, unconfirmed: the collapse/storm-brake work that
  shipped this cycle (#137, commit `04ef77c`), which governs when the seek
  re-arms and when it gives up. Supporting evidence: the field log shows two
  instances chasing **different targets (54 and 30) at the same instant**, i.e.
  disagreeing about collapsed state. Worth 20 minutes ONLY if a fast revert is
  needed to unblock the tag; moot if the redesign lands.
- **Measured runaway** (sandbox, 150-column window, trigger `Alt+t`): sidebar at
  `x=48, 95 columns` against a target of 54, **overlapping** the terminal pane
  which starts at `x=50`. Field log shows parks at **141** columns and at **11**
  columns — it runs away in BOTH directions.
- **A `Fixed`-size pane cannot be resized at all.** `resize_pane_with_id`
  silently refuses it (`CantResizeFixedPanes`) because zellij resizing IS
  percent arithmetic — `Dimension` has `set_percent` and no `set_fixed`. So
  `pane size=54` in the layout would leave `Alt+c` permanently dead. Layout
  percentages are already what clave emits.
- **There is NO absolute-resize API for TILED panes** in zellij-tile 0.44.3.
  The only absolute sizing command is `ChangeFloatingPanesCoordinates`, and the
  bar is tiled by design. Relative steps are the entire surface.
- **Zellij steps ~5% of the tab's display area (~7–14 columns) and the amount is
  NOT specifiable.** Reachable widths form a lattice `birth ± k×step`, and an
  exact column target is frequently **not on it**. This is the real reason the
  seek can never simply work: it chases a number the API cannot express.
- **The 5% figure is EMPIRICAL, not source-verified** — `zellij-server` is not
  vendored. A previously-approved change to compute the step from it was
  demoted for exactly this reason. Any dead-reckoning design inherits that bet.
- **`Decrease` does not reliably shrink.** Direction resolves against whichever
  neighbour the live layout puts on that edge; the same instance was measured
  going both ways on the identical effect, once running to ~90% of the terminal.
  The current code LEARNS the polarity. Blind dead-reckoning is unsafe here.
- **Feedback is render-only and starvable by construction.** Zellij never
  repaints an idle plugin, and a resize it REFUSES produces no repaint either.
  Laziness may key off renders; correctness may not.
- **A runaway seek passes every "did it converge" assertion** — it terminates
  with budget spent, an accepted terminal state. The assertion that catches it
  is about the JOURNEY (never move away from target twice in a row), not the
  endpoint.

### The chosen design, and why the recorded objection to it dissolves

Declare the two geometries as **swap layouts** and let zellij switch between
them (`next-swap-layout`). Zellij does the arithmetic; there is no stepping, no
feedback loop, nothing to starve. This is Ollie's "two fixed percentages"
implemented natively, and LEDGER D22 records it as **the one fundamental
alternative never run live**.

The recorded objection was that the IMPLICIT swap path is damage-gated —
`resize_pane_with_id` is itself a damage-setter, so auto-relayout stops. **That
objection dissolves precisely because this design removes all resizing:**
nothing damages a layout nobody resizes. The EXPLICIT `next-swap-layout` path
is not damage-gated at all.

Known costs, both accepted in conversation: peek-on-nav becomes a layout switch
rather than a nudge, and a `Fixed` bar would make its neighbour user-unresizable
— so use **percentages, not Fixed**.

Expected shape of the work: the three layout generators gain swap layouts; the
model DELETES the step learner, the drift gates, the polarity learning and the
storm brake; tests that pin 54 columns need updating. Net subtraction.
