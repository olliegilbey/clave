## What's Working

- **#178 is understood and fixed.** `clave-register` is a broadcast, and a
  broadcast reaches only instances ALREADY RUNNING when it fires. A tab born by
  a wake never hears about its own pane; every instance that did hear is by then
  a background instance, which cannot see a pane outside its own tab. Knowledge
  and visibility land in different bars and the join silently fails. The fix
  puts the pane id on the store snapshot, which every instance hydrates at load.
- **The #184 instrumentation did its job** and should stay. It named the state
  (`PaneKnownButAbsent`) on the first field reproduction.
- **The bar already logs the width runaway** — grep `WIDTH SEEK CAPPED` in the
  zellij log. That is the fastest route into #181 and it existed all along.

## Important Discoveries

- **The width runaway is NOT new to the instrumented build.** The 141-column
  park logged at 15:11 predates the 15:21 wasm swap. It is in shipped v0.1.3.
- **Measured #181, from the sandbox** (150-col window, trigger `Alt+t`):
  sidebar at **x=48, 95 columns** against a target of 54, overlapping the
  terminal pane which starts at x=50. Field log shows parks at **141** and at
  **11** columns, and two instances chasing **different targets (54 and 30)
  at the same instant** — i.e. they disagreed about collapsed state, which is
  a live candidate for what keeps re-arming the seek.
- **THE CONSTRAINT THAT KILLS THE OBVIOUS FIX — read before designing.**
  A `Fixed`-size pane cannot be resized at all: `resize_pane_with_id` silently
  refuses it (`CantResizeFixedPanes`), because zellij resizing IS percent
  arithmetic and `Dimension` has `set_percent` and no `set_fixed`. So
  `pane size=54` would leave `Alt+c` permanently dead. Layout percentages are
  already what clave emits.
- **There is no absolute-resize API for TILED panes in zellij-tile 0.44.3.**
  The only absolute sizing command is `ChangeFloatingPanesCoordinates`, and the
  bar is tiled by design. Relative steps are the entire surface.
- **Zellij steps ~5% of the tab's display area (~7–14 columns), and the amount
  is not specifiable.** Reachable widths therefore form a lattice
  `birth ± k×step`, and **an exact column target is frequently not on it** — at
  280 columns the expanded bar can only rest at 47 against a target of 54. This
  is the real reason the seek can never simply "work": it is chasing a number
  the API cannot express.
- **The step's 5% figure is EMPIRICAL, not source-verified** (`zellij-server`
  is not vendored). A previous approved change to compute the step from it was
  demoted for exactly this reason. Any dead-reckoning design inherits that bet.
- **`Decrease` does not reliably shrink.** Direction resolves against whichever
  neighbour the live layout puts on that edge; the same instance was measured
  going both ways on the identical effect, once running to ~90% of the
  terminal. The current code LEARNS the polarity. Blind dead-reckoning would
  be unsafe here.
- **The one fundamental alternative never run live is `next-swap-layout`**
  (LEDGER D22): declare the two geometries as swap layouts and let zellij
  restore them. No stepping, no feedback, no drift — this is Ollie's "two fixed
  percentages" implemented natively. Known costs on record: peek-on-nav becomes
  a layout switch, and a `Fixed` bar would make its neighbour user-unresizable
  (use percentages, not Fixed). The IMPLICIT swap path is damage-gated and dead
  on arrival; the EXPLICIT `next-swap-layout` path is not damage-gated and is
  the live candidate.
- **Feedback is render-only and starvable by construction.** Zellij never
  repaints an idle plugin, and a resize it REFUSES produces no repaint either.
  Any design whose CORRECTNESS waits on renders is starved. Laziness may key
  off renders; correctness may not.
- **A runaway seek passes every "did it converge" assertion** — it terminates
  with budget spent, which is an accepted terminal state. The assertion that
  catches it is about the JOURNEY (never move away from target twice in a row),
  not the endpoint.
- **The sandbox cannot reproduce multi-instance bugs.** Its fleet has one
  sidebar across all tabs; the real fleet has one per tab. Filed as #186. Treat
  any sandbox green on an instance-interaction bug as meaningless.
