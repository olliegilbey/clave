**#193's review found a hole, and it is now issue #195.** The store can only
forget a pane when the row was *bound* to the tab that died. An agent that

## The big one — #181, built, not pushed

Branch `redesign-181-swap-layout-width`. **719 lines added, 2,130 removed.** All
four gates green, 421 workspace tests, mutation testing 28 of 28 caught.

The sidebar no longer chases a column count. Both widths are written into the
generated layouts as two alternative pane arrangements, and collapsing asks
zellij to switch between them — zellij does the arithmetic, the bar issues one
instruction and never watches the result. Deleted outright: the step learner,
the polarity learner, the drift gates, the storm brake, the width seek.

**The accepted cost:** the bar is a whole percentage of the window, so it can
land a column either side of the intended width and stay there. Nothing corrects
it any more. That is the point.

**Both open questions are now ANSWERED from real source.** The switching code
lives in `zellij-server`, which is not vendored; an agent fetched the matching
0.44.3 crate from crates.io (unpacked in `/tmp`, nothing added to the workspace)
and read it. The installed zellij is Homebrew 0.44.3, so the versions match.

1. **Does the switch re-use the running sidebar, or start a second copy?**
   It re-uses it. A swap moves the already-running plugin pane into the new
   geometry and has no channel for creating plugins at all. One condition: both
   geometries must declare the plugin identically — only the size may differ,
   because a pane's identity is its location plus its configuration.
   *The core bet of the redesign is sound.*

2. **Does one sidebar's switch apply to its own tab, or the focused one?**
   **The focused one. This is a real bug in the branch as written.** The
   plugin's request does carry its own identity, but the server's routing layer
   discards it and resolves the switch against whatever tab that client is
   looking at. A sidebar on a background tab would resize a different tab's bar.
   There is no tab-scoped version available to plugins — it exists only as a
   command-line action.

   The branch currently asserts the opposite in a comment
   (`crates/clave-bar/src/main.rs:665`), and background sidebars do reach this
   path: mode changes arrive at every sidebar through the store snapshot, and
   hidden sidebars still render.

   **Smallest honest fix, and the one being applied:** issue the switch only
   when the sidebar's own tab is focused, and hold a pending switch until it
   becomes focused. That is a gate on state the model already tracks, not new
   machinery. Routing through the command-line form with an explicit tab number
   would work but is heavier and reintroduces process spawning.

Both findings are recorded in `FOOTGUNS.md` on branch
`footguns-181-swap-layout-scoping` (commit `91a5410`), also waiting on a push.

**Only you can confirm the whole thing live**, but it is no longer a guess.

## The width redesign was reviewed hard, and needed it

An agent that had not written it reviewed the branch against zellij's real
source, re-ran the gates and re-ran mutation testing independently. Verdict:
**ship after fixes.** The deletion is genuinely complete — all fourteen
seek fields, all three effects and the whole simulation harness are gone, and
nothing calls a resize anywhere. Findings, being fixed now on a stacked branch:

- **`Alt+a` births its sidebar 40% too wide, permanently.** That line is
  unchanged by this branch, but the deleted seek is what used to correct it, so
  removing the seek turns a cosmetic gap into a permanently wrong width on the
  main way you create agents. On your 280-column display: 75 columns instead of
  54. The dwell-open path already does this right; `Alt+a` is getting the same.
- **Two tests were silently emptied.** Layouts used to contain one width and now
  contain three, so assertions that were once precise can no longer fail. The
  guard for "a fleet left collapsed must be born collapsed" would pass with the
  feature removed entirely.
- **The expand direction was untested** — the reviewer's independent mutation
  run was 26 of 27, not the claimed 28 of 28. If a switch to the wide layout
  leaves the pane unmoved, the bar draws wide text into a narrow pane.
- **The minimum width you asked to keep only half survived.** It works at
  launch; resize the window afterwards and nothing brings the bar back. Halve
  the window and the wide bar ends up narrower than the collapsed one.
  **I instructed documentation rather than a fix** — preserving it across a
  resize means watching and correcting, which is exactly what this change
  deletes. **This is your call and you may want more.**

**One simplification I deliberately did not build.** Zellij will tell a plugin
which of the two layouts its tab is in, by name, synchronously. The branch
instead keeps a one-render "did the pane move the way I wanted" check — the last
surviving piece of the watch-your-own-repaints pattern. Switching to the
absolute signal would delete it. Not a recorded dead end; worth doing, but not
as scope creep on a branch already in review.
