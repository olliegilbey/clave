## NEW SIGHTING — cross-session bleed (uninvestigated, potential new issue)

Ollie, 2026-08-12 evening, verbatim: "interactions such as switching tabs
in my main clave session causes resizes of panes in the worktree sandbox
while it's still up. This is a bad sign, it's meant to be isolated …
I haven't interacted with the sandbox session at all, so anything that's
moving there is being driven by me in my normal clave session."

Two zellij sessions ("clave" + "clave-test-qa-182-d-1d57"), separate
stores/configs by design; something his session does reaches the sandbox's
panes. Config hot-reload is a designed mechanism — cross-SESSION bleed is
not. Suspect classes to check first: a shared path in the generated
configs (plugin wasm/theme/cache), zellij's per-user shared runtime state,
or a push/pipe leg that addresses the wrong session (the "one leak"
family, #43/#44, FOOTGUNS 112). File as an issue once a bleed path is
named; it may bear on #181 (external resizes = a candidate "external
mover", B4/D37).

Explored at handoff time (log reads + process env inspection), findings:

- Nothing inside the sandbox root changed after 17:28:24 (clave.log and
  qa/ silent; find -newermt empty) — whatever moves the panes leaves no
  store/log trace in the sandbox instance.
- **DISPROVEN: env leak into the main server.** Both zellij servers'
  environments inspected via `ps aexww`: the `clave` server carries NO
  `CLAVE_SESSION`; only the sandbox's own server carries
  `clave-test-qa-182-d-1d57` (by design). So bar-spawned `clave`
  subprocesses in his session resolve to HIS session — that path is clean.
  (Bar subprocess env note for the record: `clave-bar/main.rs` spawns
  `run_command` with an EMPTY env map, inheriting the server's ambient
  env; `env::session_name()` is pure `$CLAVE_SESSION`; open.rs/hook set
  `ZELLIJ_SESSION_NAME` explicitly from that. #161's respect-env doc
  comment names the split-brain risk class; FOOTGUNS:220 relies on
  per-worktree isolation as the structural guard.)
- **LEAD HYPOTHESIS — the shared zellij cache.**
  `~/Library/Caches/org.Zellij-Contributors.Zellij/` is ONE tree for all
  sessions, and `permissions.kdl` in it is ONE file unconditionally
  shared (`setup.rs:440-447` merges grants into it; live file holds
  grant entries for the stable wasm AND six sandbox wasms). Its mtime is
  2026-08-13 08:38 — rewritten while the sandbox was up. If zellij
  hot-reloads permissions/cache state, a rewrite triggered by main-session
  activity would fan out to EVERY live session; the sandbox bars would
  re-render/re-seek → the observed resizes. Confirming evidence: correlate
  the next observed sandbox resize with a fresh permissions.kdl/cache
  mtime; or trace which main-session interaction rewrites the cache
  (a `clave setup`/doctor leg, or zellij's own session-info writes).
- Third hypothesis (weaker): an orphaned pipe/`run_command` subprocess
  from the 17:28 drive still in flight — check `ps` for argv/env carrying
  `qa-182-d-1d57` beyond the two legitimate server/client processes.
