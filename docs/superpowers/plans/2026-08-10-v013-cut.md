## Task 1: #148 — the sidebar viewport

Branch `feat/148-viewport`, worktree `.claude/worktrees/148-viewport`.

The sidebar gets a **viewport** (UBIQUITOUS_LANGUAGE §3.5): chat-app
scrolling. Full spec is the `/to-spec` comment on issue #148 (read it with
`gh issue view 148 --comments`; it is the contract). The operative rules:

- The list rests at the top; rows overflow off the bottom only.
- It scrolls only when the selection walks past the bottom edge, keeping two
  rows of **lookahead** below the selection when rows exist below; walking
  back up returns it; when the selection fits the first screenful the view
  snaps home to the top.
- The renderer consumes the pane height it already receives
  (`render(rows, cols)` in the plugin shell) and slices the existing flat
  row list. Ordering unchanged. Derived state in the pure model/render
  layer; no zellij scroll API.
- Mouse-click row mapping shifts by the same offset (the shell maps clicked
  line → row today). Collapsed mode reuses the identical slice at the same
  heights. No overflow markers (descoped, by maintainer ruling — see the
  design-lock comment on #148).
- A snapshot arriving while scrolled must not yank the view: the slice
  re-clamps only as far as needed to keep the selection visible.

Seam (pre-agreed with maintainer): the pure boundary where the model hands
the row list to the renderer — synthetic rows + pane height + selection in,
visible lines out, exactly as the existing goldens drive it. No new seams.

Tests: proptest invariant (selection always within the visible window;
lookahead honoured when satisfiable); goldens for selection riding the
bottom edge, the slide, the snap home, collapsed mode, degenerate heights
(0, 1, exactly-fitting). Red-first. `just gates` + mutants over the diff.

Out of scope: overflow indicators, pinned/split live block, scroll-wheel
input, any live sandbox driving.

## Task 3: #162 — diagnosis of broadcast-pipe starvation (READ-ONLY)

No worktree, no code changes, no commits. Deliverable is a written diagnosis.

Symptom (issue #162 has full evidence): in a zellij session where every
launch-time bar instance has died, broadcast pipes and bar-to-bar beacons
arrive with EMPTY payloads at every surviving instance — including freshly
created ones — so the executor election never fires and the whole effect
surface (focus, wake, announce) goes dark. Only payload-less instance-local
keys still work.

Questions to answer, from the vendored source
(`~/.cargo/registry/src/*/zellij-*-0.44.3/`, start at the wasm_bridge pipe
routing):

1. Does zellij's pipe fan-out deliver payload copies to dead clients' slots
   (ghosts), or only to the first-N registrations? Cite file:line.
2. Given the answer, which clave-side mitigation is sound: the beacon riding
   the store (seq-stamped, like snapshots), a lone-instance-elects-itself
   fallback keyed on the tab set, or something better the source suggests?
3. What is the cheapest honest repro/verification path once a fix exists?

Also read clave's side: the pipe entry points in the plugin shell, the
executor-election beacon in the model, and the #128 empty-payload guard.
Deliverable: a diagnosis report (mechanism with citations, recommended fix
design with trade-offs, verification plan) written to the report file — the
principal reviews it before any implementation is scheduled. Do not post to
GitHub; the principal does that after review.

## Task 4: #105 — expanded-view battery as a 4-column token count

BLOCKED BY Task 1 (shared goldens and width arithmetic — scheduling edge).
Branch and worktree minted at dispatch time.

Expanded view renders the battery cell as a right-aligned 4-column token
count in the ramp's ink; collapsed keeps the glyph. This is a real width
change: the cell goes 1→4 columns and the gutter arithmetic moves with it —
`min_intact_cols`, the column map, `Widths::EXPANDED`, the goldens and the
preview all derive from the same numbers. Summary is the only flexible
column (LEDGER D9). Issue #105 has the full design.

Formatting rulings (maintainer-approved defaults): bare `1m`, never `1.0m`;
unknown count renders blank; the colour ramp keeps its five buckets.

Tests at the same pure seam: goldens under both profiles, the four-character
range examples from the ticket (`1k`, `400k`, `999k`, `1m`, `1.1m`),
red-first, gates + mutants.
