# Clave multi-provider design: Claude Code + Codex CLI

**Status:** approved in brainstorming on 2026-07-21; reconciled on 2026-07-22
with `v0.1.1` and main at `ccd67fb`; implementation plan pending.

## 1. Verdict

Extending Clave to support Codex CLI alongside Claude Code is viable. The bar,
status model, recency ordering, Zellij integration, and atomic JSON store are
already mostly provider-neutral. The coupling is concentrated in `add.rs`,
`spawn.rs`, `hook.rs`, `setup.rs`, `env.rs`, and the identity assumptions in
`store.rs`/`clave-types`.

The correct change is a provider-adapter refactor, not Codex conditionals added
throughout the existing Claude flow. Claude and Codex remain the only built-in
providers for this work, but the boundary must make a later provider a local
addition rather than another cross-cutting rewrite.

The assessment used:

- the current Clave implementation and canonical design;
- the installed Claude Code `2.1.217` and stable Codex CLI `0.144.5` at
  `~/.bun/bin/codex`;
- Codex's current official manual;
- JSON schemas generated by that CLI's `app-server` command.
- released Clave `v0.1.1` plus the `ccd67fb` plain-terminal follow-up;
- the parallel installer/doctor design and its shared executable resolver.

The shell currently resolves `/opt/homebrew/bin/codex` first, which is the old
`0.44.0` binary. Provider probing must detect and explain this class of PATH
shadowing rather than silently launching an incompatible executable.

## 2. Goals

1. Run Claude and Codex agents side by side in one Clave/Zellij session.
2. Order all tabs and dormant conversations in one recency timeline.
3. Discover and resume conversations created outside Clave.
4. Keep the real Claude or Codex TUI in each pane.
5. Preserve Zellij and Clave operation over SSH with no desktop dependency.
6. Keep provider-owned conversation data in provider-owned storage.
7. Confine upstream CLI changes to the corresponding adapter and fixtures.
8. Preserve current Claude behavior through an explicit store migration.
9. Preserve plain `Alt+t` terminal tabs as non-agent tabs.

## 3. Non-goals

- A user-installable or dynamic provider plugin ABI.
- Reimplementing either provider's TUI, transcript, or conversation store.
- Running Codex through the desktop app.
- Keeping an app-server daemon alive for normal rendering or status.
- Importing every discovered conversation into Clave automatically.
- Unifying provider-specific model, sandbox, permission, or account settings.
- Implementing install and doctor in this worktree; those are being developed
  separately and consume the contracts defined here.

## 4. Invariants

1. **The provider TUI is real.** Clave launches the installed CLI in the
   Zellij PTY and never screen-scrapes it.
2. **The core is provider-blind.** Store mutation, status, recency, bar
   rendering, focus, navigation, and Zellij topology use only core types.
3. **Identity has two layers.** `AgentId` is Clave-owned. A
   `(ProviderKind, ProviderSessionId)` pair identifies a provider conversation.
4. **Conversation data remains external.** Clave stores no turns, tool calls,
   reasoning, transcript bodies, or raw provider records.
5. **The hot path is local and event-driven.** Bar hydration reads Clave's
   tiny index; provider discovery runs only for add/resume/reconciliation.
6. **One provider may fail independently.** A failed probe or discovery does
   not block the other provider or an already-running fleet.
7. **SSH is a first-class environment.** Every required process and file lives
   on the host running Zellij. No GUI, local desktop bridge, port forwarding,
   or persistent localhost service is required.
8. **Upstream formats are adapter details.** No provider command, hook payload,
   storage path, or protocol shape leaks into the bar or core store API.
9. **Plain terminals remain plain.** `Alt+t` creates a normal Zellij tab with
   a bar, but no provider, agent row, lifecycle hooks, or discovery semantics.

## 5. Architecture

Introduce a compile-time provider registry with two implementations:

```text
provider/
  mod.rs       core contract and built-in registry
  claude.rs    Claude discovery, commands, hooks, capability probe
  codex.rs     Codex discovery, commands, hooks, capability probe

agent.rs       provider-neutral create/import/open orchestration
events.rs      normalized lifecycle events and core state transitions
discovery.rs   merge, deduplicate, scope, and recency-sort provider results
store.rs       versioned cross-provider materialized index
```

The contract is conceptually:

```rust
trait ProviderAdapter {
    fn kind(&self) -> ProviderKind;
    fn probe(&self, executable: &Executable) -> ProbeReport;
    fn discover(&self, scope: &DiscoveryScope) -> Result<Vec<DiscoveredSession>>;
    fn launch(&self, request: &LaunchRequest) -> Result<CommandSpec>;
    fn hook_specs(&self, launcher: &Path) -> Vec<HookSpec>;
    fn normalize_hook(&self, event: &str, payload: &[u8]) -> Vec<AgentEvent>;
}
```

This is an internal Rust interface, not a stable public ABI. Provider-specific
types remain inside their module. The registry is exhaustive over
`ProviderKind::{Claude, Codex}`, so unsupported cases fail at compile time.

Core interchange types are deliberately small:

- `DiscoveredSession`: provider, native session ID, cwd, display label,
  provider recency, and optional source metadata needed for filtering.
- `CommandSpec`: executable, exact argv, cwd, environment additions, and
  whether the request creates or resumes.
- `ProbeReport`: resolved executable, version, capabilities, and actionable
  compatibility problems.
- `AgentEvent`: `SessionIdentified`, `TurnStarted`, `NeedsInput`,
  `TurnCompleted`, `TurnFailed`, `LabelSuggested`, and `SessionExited`.

## 6. Store ownership and minimal schema

The dedicated store remains, but its role is explicitly a small materialized
cross-provider coordination index.

### 6.1 Durable Clave-owned fields

- `AgentId`;
- `ProviderKind` and optional `ProviderSessionId`;
- normalized status;
- `last_visited` for unread handling;
- whether Clave created/owns a worktree;
- stale/open failure state.
- global bar `collapsed` state.

The provider session ID is temporarily absent only while a new provider that
mints its own ID (Codex) is starting.

### 6.2 Cached discovery and presentation fields

- canonical cwd;
- repo root and branch derived from that cwd;
- display label;
- normalized `last_interacted`.

These values are cached because cold-start rendering and dormant opening must
be instant and must still work when a provider probe is temporarily broken.
Discovery and live hooks refresh them. They are not treated as authoritative
conversation content.

### 6.3 Session-scoped coordination fields

- Zellij tab/pane binding;
- tab recency timeline;
- monotonic snapshot sequence.

They may live in the same atomic JSON document because independent hook
processes and bar instances need one convergence point, but they are cleared or
rebound when the Zellij session is recreated. The released exact-dead-tab
pruning and bind-collision handling provide the session boundary; no new
session epoch is introduced.

### 6.4 Fields removed from the core

- Claude-specific `LabelSource`;
- the assumption that one `uuid` is simultaneously Clave identity, provider
  session identity, transcript filename, and resume argument;
- provider transcript paths or raw discovery/status objects.

The store remains JSON plus the existing stable lockfile and atomic rename.
Expected size is kilobytes for a normal fleet. Replacing it with provider scans
would increase latency and I/O while losing durable unread and Zellij state.

## 7. Store migration

Add an explicit schema version and a typed V1-to-V2 migration:

- every V1 row becomes `ProviderKind::Claude`;
- the old UUID becomes both the new `AgentId` value and Claude's
  `ProviderSessionId`, preserving all current joins;
- cwd, repo root, branch, label, timestamps, worktree ownership, status,
  binding, stale state, tab timeline, and global `collapsed` state are
  preserved;
- `LabelSource` is consumed during migration but is not written to V2;
- migration uses the same lock and atomic write path as normal mutation;
- no row or provider conversation is deleted as part of migration.

The V1 reader exists only at the store boundary. No compatibility branches are
allowed through the rest of the core.

## 8. Discovery and unified resume

`clave add` continues to begin with cwd selection. The resume path calls both
enabled providers concurrently with bounded timeouts, then:

1. normalizes each result to `DiscoveredSession`;
2. derives/caches git repo and branch information from its cwd;
3. scopes results to the selected repository, including its worktrees;
4. deduplicates by `(ProviderKind, ProviderSessionId)`;
5. joins any existing Clave record;
6. marks a matching live Clave agent as a jump target;
7. sorts the merged list by normalized recency descending;
8. shows a provider marker in the resume picker and `clave ls`.

Repository scope reuses the released worktree-aware algorithm: run
`git worktree list --porcelain`, treat its first record as the main checkout,
scan every registered worktree plus the picked directory, and preserve each
candidate's true cwd and branch. It must not regress to exact-cwd matching or
use a linked worktree's `rev-parse --show-toplevel` as the repository identity.

Only the selected external conversation is imported into the Clave index.
Discovery alone does not make every provider conversation a dormant bar row.

### 8.1 Claude discovery

The Claude adapter owns the current physical-cwd munging and
`~/.claude/projects` layout. It may use `sessions-index.json` as a best-effort
index and bounded JSONL reads where the index is stale. The core receives only
the normalized ID, cwd, label, and recency.

### 8.2 Codex discovery

The Codex adapter starts a short-lived `codex app-server --listen stdio://`
child, performs the initialize handshake, calls V2 `thread/list`, paginates,
and exits the child. The installed `0.144.5` schema supplies:

- thread ID and session ID;
- cwd;
- optional name and first-message preview;
- `createdAt`, `updatedAt`, and `recencyAt`;
- source, model provider, and runtime status.

Clave uses the thread ID accepted by `codex resume`, cwd, name-or-preview, and
`recencyAt` (falling back to `updatedAt`). It ignores the explicitly unstable
on-disk `path` and does not persist raw runtime status. Interactive sources are
included; non-interactive exec runs and subagents are excluded initially.

The app-server command is currently experimental. Its minimal use is contained
in `codex.rs`, parsed tolerantly (unknown fields ignored), version/capability
checked, timeout-bounded, and covered by fixtures generated from supported CLI
versions. If it breaks, external Codex discovery degrades without breaking
tracked-session resume or Claude.

## 9. Commands and lifecycle

### 9.1 User-facing flow

- `clave add`: choose cwd, then new or unified resume.
- New: choose Claude or Codex, create a Clave row, and open its tab.
- Resume: select a merged result; jump if already live, otherwise upsert the
  selected record and open its tab.
- `clave ls`: retain the unified recency order and add a provider marker.

The bar remains narrow; a provider marker is required in selection/listing but
is not required in every bar row for the first implementation.

### 9.2 Internal commands

- `clave spawn <agent-id>` reads the record and delegates command construction.
- `clave open <agent-id>`, `focus`, `bind`, and `touch` remain generic.
- hooks use `clave hook <provider> <event>`.
- `clave setup` delegates hook definitions to enabled adapters while preserving
  unrelated provider configuration.

No KDL contains provider commands or provider session IDs. It contains only
the stable Clave launcher and `AgentId`.

### 9.3 Exact provider commands

The adapter constructs argv without a shell:

- Claude create: `claude --session-id <provider-id>` — **no `--name`**, and an
  adapter must not reintroduce one. Claude records it as a `custom-title` that
  the hook cannot tell from a user `/rename`, so it filled the bar's title chip
  on an agent nobody had named, and it overwrote the `aiTitle` that Claude's own
  resume picker falls back to (#91, dropped in #90). clave never titles a
  session at birth; the chip stays blank until the user renames it;
- Claude resume: `claude --resume <live-provider-id>` — the id the conversation
  is using NOW, which is not the minted one once the pane has been `/clear`ed.
  Any provider whose sessions can rotate an id needs the equivalent of
  `AgentRecord::live_session` and `spawn::resume_target` (#99);
- Codex create: `codex -C <cwd>`;
- Codex resume: `codex resume -C <cwd> <provider-id>`.

Executable resolution uses the installer/doctor's single shared resolver:
`$CLAVE_<PROVIDER>_BIN` override, then global PATH lookup, then curated known
locations. Thus Codex uses `$CLAVE_CODEX_BIN` and Claude uses
`$CLAVE_CLAUDE_BIN`. Off-PATH finds are launched by absolute path. Adapters
never duplicate lookup logic or hardcode a local username; the probe reports
PATH shadowing when a different older executable wins.

### 9.4 Codex-created identity

Codex does not accept a caller-supplied ID for a new interactive session.
Clave therefore creates a provisional row containing `AgentId` and provider,
then launches Codex with `CLAVE_AGENT_ID` in its environment. The Codex
`SessionStart` hook supplies the generated `session_id`; the hook atomically
attaches it to the provisional row before later lifecycle events are applied.

Environment inheritance and event order are validation gates, not assumptions.
If the custom variable is not inherited, the spike must validate correlation
through inherited `ZELLIJ_PANE_ID`; if neither is available, the Codex adapter
must use app-server launch correlation rather than weakening core identity.

### 9.5 Process supervision

`clave spawn` supervises and waits for the provider process with inherited
stdin/stdout/stderr and the Zellij PTY. It emits a normalized exit/failure
event and then exits with the provider result. This replaces core dependence on
provider-specific `dump-layout` argv parsing and covers providers without a
`SessionEnd` hook.

PTY behavior, signals, pane close, Zellij reconnect, and SSH disconnect are
live-validation gates before replacing the current `exec` path.

## 10. Hooks and normalized state

Provider hook setup is separate; core state transitions are shared.

| Core event | Core effect | Claude source | Codex source |
|---|---|---|---|
| `SessionIdentified` | attach native ID; idle | pre-minted / `SessionStart` | `SessionStart` |
| `TurnStarted` | working; bump recency/timeline | `UserPromptSubmit` | `UserPromptSubmit` |
| `NeedsInput` | needs-you | permission/notification events | `PermissionRequest` |
| `TurnCompleted` | done/unread | `Stop` | `Stop` |
| `TurnFailed` | failed | failure event/process exit | hook payload/process exit |
| `SessionExited` | settle non-running state | supervisor/`SessionEnd` | supervisor |
| `LabelSuggested` | update cached label by quality | prompt/summary | prompt/name/preview |

Unknown events, missing IDs, malformed payloads, and untracked sessions are
successful no-ops. A Clave hook must never break the provider's agent loop.
Label eligibility is adapter-owned: the Claude adapter preserves the released
label-state rules and rejects injected `<task-notification>` prompts, while the
core receives only an eligible `LabelSuggested` event.

Codex hooks are a stable feature in `0.144.5`, but command hooks are
trust-gated. Hook definitions must reference a stable Clave launcher path; a
versioned path in the hook text would change its trust hash on every release.
The stable launcher is supplied by the parallel install work. Setup merges
hooks, and doctor reports untrusted or disabled hooks through the adapter's
probe contract.

## 11. Zellij topology and liveness

Provider process argv is not a generic liveness interface. Remove
`live_uuids` parsing of `claude --session-id`/`--resume` from the core.

Preserve and genericize the released bind/prune path:

1. `clave spawn <AgentId>` gives the bar a provider-neutral pre-bind token;
2. the active bar joins it to the live Zellij tab and persists
   `AgentId -> tab_id`;
3. `tab_id` is the authoritative live bind; `apply_bind` evicts collisions
   because Zellij reuses tab IDs;
4. Tab updates report exact disappeared IDs to `apply_prune_tabs`; its
   remove-listed operation remains idempotent, commutative, change-gated, and
   re-emitted until the store echoes the removal;
5. the existing open guard plus current bind prevents duplicate dormant opens.

Any dump-layout fallback is additive and may recognize only the stable
`clave spawn <AgentId>` command. Core liveness never parses Claude or Codex
argv. Plain terminal tabs participate in Zellij topology but never acquire an
agent bind.

Thus Zellij is authoritative for live topology, providers are authoritative for
conversation persistence, and Clave's store joins the two. Adding a provider
does not require teaching the liveness layer its command-line syntax.

## 12. SSH and resource model

All commands execute on the host running the Zellij server. Over SSH:

- disconnecting the client leaves Zellij and provider processes running;
- reconnecting and running `clave` reattaches to the same session;
- hooks update the remote Clave index and remote bar;
- provider discovery reads the remote provider account/state;
- worktrees and cached records remain remote;
- Codex app-server uses child-process stdio only and exists only during
  discovery.

Normal bar work is one small JSON read on hydration plus snapshot pushes on
events. No provider scan, app-server, polling loop, network listener, or daemon
is part of rendering. Discovery calls both providers in parallel only when the
user asks for resume candidates.

## 13. Failure behavior

- Probe failure disables only that provider's new/discovery actions and gives
  the exact resolved executable/version problem.
- Discovery timeout returns the other provider's results plus a concise
  warning.
- A missing provider conversation marks its Clave row stale; it is not deleted.
- A failed new-session identity attachment fails that provisional row visibly
  rather than guessing a session.
- Unsupported protocol changes produce an adapter capability error containing
  provider version and failed operation.
- Hooks always exit successfully after best-effort logging.
- No operation archives, deletes, or edits provider conversation history.
- Existing tracked rows remain renderable when provider discovery is offline.

## 14. Validation strategy

### 14.1 Automated tests

- provider contract tests run identically against Claude and Codex fixtures;
- golden command tests pin exact executable/argv/cwd/environment construction;
- hook fixture tests pin normalization and malformed-payload no-ops;
- discovery fixtures pin pagination, filtering, deduplication, labels, and
  cross-provider recency;
- store tests pin V1 migration, identity separation, atomicity, and minimal
  serialization;
- bar tests use only `AgentId` and provider-neutral snapshots;
- partial-failure tests prove one provider cannot block the other;
- capability tests cover missing, shadowed, old, and compatible executables.
- compatibility tests deserialize pre-release snapshots (including the
  serde-defaulted `collapsed` field) across the stable launcher/versioned CLI
  and bar boundary.

### 14.2 Required live spikes

1. **Codex hooks:** capture `SessionStart`, `UserPromptSubmit`,
   `PermissionRequest`, and `Stop` payloads; verify ordering, session ID,
   custom environment or pane-ID inheritance, no-op output, and trust flow.
2. **Codex discovery:** initialize app-server over stdio, paginate
   `thread/list`, import an external CLI session, and resume it by returned ID.
3. **Provider supervision:** run each real TUI under `clave spawn`, exercise
   prompt/approval/stop/exit, close a pane, and verify no zombie or signal
   regression; verify Ctrl+Q fleet shutdown reaches both provider children.
4. **Zellij/SSH:** disconnect and reconnect an SSH client while both providers
   run; verify status, recency, input, dormant open, and cold reattach.
5. **Mixed fleet:** interleave Claude and Codex prompts and prove one total
   recency order across live tabs, dormant rows, `clave ls`, and resume results.
6. **Topology regression:** close/reuse tab IDs under concurrent prune writes,
   verify binds converge, and prove `Alt+t` remains a plain terminal with no
   agent row.

Repository safety rules still apply during validation: the coding agent prints
live Zellij lifecycle commands for the maintainer instead of launching or
killing sessions. This does not change the product behavior whereby a user
invoking bare `clave` asks Clave to attach/create its dedicated session.

## 15. Install and doctor integration boundary

The parallel install/doctor work owns:

- installation of the stable Clave launcher used by KDL and trusted hooks;
- user-facing provider executable configuration storage;
- presentation of provider and hook health.
- the shared resolver (`$CLAVE_<TOOL>_BIN`, PATH, curated locations) and stable
  launcher/versioned-runtime split.

This provider work supplies:

- `ProbeReport` and capability definitions;
- hook specifications and merge routines;
- exact executable resolution results;
- provider discovery/launch diagnostics.

There must be one probing implementation consumed by setup, add/resume, and
doctor—not parallel versions that drift. Doctor reports Claude and Codex
independently; bare launch requires at least one enabled, compatible provider,
not Claude specifically. Setup merges hooks only for enabled/discovered
providers and preserves unrelated configuration. Provider hook checks are
adapter-defined facts rendered by doctor, while executable resolution remains
owned by the shared installer/doctor layer.

## 16. Viability risks and containment

| Risk | Assessment | Containment |
|---|---|---|
| Codex app-server is experimental | Medium | Minimal `thread/list` client isolated in Codex adapter; tolerant parsing, fixtures, timeout, graceful degradation |
| Codex new ID is provider-minted | Medium | `SessionStart` correlation spike; explicit provisional state; no guessed joins |
| Hook event details change | Low/medium | Provider normalization fixtures and capability probe; unknown events no-op |
| Hook trust changes on upgrade | Low if launcher stable | Stable hook command supplied by installer; doctor reports trust state |
| Supervisor affects TUI/PTY | Medium until spike | Preserve inherited PTY; validate both TUIs, signals, Zellij, and SSH before migration |
| Existing Claude state migration | Low | Explicit typed V1 migration preserving old UUID as both identities |
| PATH resolves an old CLI | Observed | Shared override/PATH/known-location resolver and version/capability report |
| Released bind/lifecycle behavior regresses | Low if reused | Keep exact-dead-ID prune, collision eviction, plain-terminal invariant, and mixed-fleet topology tests |

None is an architectural blocker. The live spikes are gates for implementation
details, while the adapter/store boundaries remain valid under each fallback.
