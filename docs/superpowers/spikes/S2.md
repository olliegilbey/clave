# Spike S2 — uuid→pane→tab join

**Purpose:** prove the plugin can turn a displayed agent row into a focus jump:
`uuid → pane_id` (from `clave-register`) → live tab position (from `PaneManifest`)
→ `go_to_tab`, and that the mapping survives tab reorder/close.

**Verdict: PENDING (awaiting interactive validation).** Code is written and builds
clean; a human must drive the actual Zellij session (this spike is human-in-the-loop
— the authoring agent did not launch Zellij).

## How to run

1. Build the plugin (already done by the authoring pass, re-run if you change the code):
   ```bash
   cargo build -p clave-bar --target wasm32-wasip1
   ```
2. Launch. **Do NOT use `zellij --session clave-s2 --layout ...`** — with `--layout`,
   `--session <name>` means "add tabs to the EXISTING session `<name>`" and errors if
   it doesn't exist yet (this is a correction to the original task brief, verified
   during S1). The **correct** form:
   ```bash
   zellij -s clave-s2 -n "$(pwd)/spikes/layouts/s2.kdl"
   ```
3. **Permissions are pre-granted — no approval prompt expected on this machine.** The
   plugin requests all THREE of `ReadCliPipes` + `ReadApplicationState` +
   `ChangeApplicationState`, and all three are already granted to this exact clave-bar
   wasm path in `~/Library/Caches/org.Zellij-Contributors.Zellij/permissions.kdl`
   (done during S1; confirmed present under the `file:...` key that matches the
   layout's `plugin location="file:..."` form before this spike started). If Zellij
   prompts anyway, the cache entry may be stale/keyed differently — approve and note
   it below. On a CLEAN machine (empty permissions cache), all three MUST be granted
   or the join silently fails (see the `ReadApplicationState` note under API/permission
   findings).
4. The `u1`/`u2` panes each print their registration line
   (`pane $ZELLIJ_PANE_ID registering as uuid=u1`, etc.) on launch.
5. Drive the nav join from any pane:
   ```bash
   zellij pipe --name clave-nav -- '{"uuid":"u2"}'
   ```
   Expected: focus jumps to the **u2** tab. Then try:
   ```bash
   zellij pipe --name clave-nav -- '{"uuid":"u1"}'
   ```
   Expected: focus jumps to **u1**.
   **Note:** `zellij pipe` is a bidirectional pipe and may not return you to the shell
   prompt after the command completes — the plugin-side effect (the focus jump)
   happens regardless of whether the pipe call returns. `Ctrl-C` reclaims the prompt
   if it hangs.
6. Resilience test: reorder a tab (`Alt`+move-tab keybind, or Zellij's move-tab
   action) and/or close the `u1` tab, then re-run the `u2` nav pipe from step 5.
   Expected: focus still lands on u2 correctly — the `PaneUpdate` subscription keeps
   `pane_to_tab` current on every change. Navigating to a closed uuid (e.g. `u1` after
   closing its tab) is an acceptable no-op for the spike.
7. Teardown:
   ```bash
   zellij delete-session clave-s2 --force
   ```

## zellij-tile API deltas

**None — the brief's Step 2 code compiled verbatim** against `zellij-tile 0.44.3` /
`zellij-utils 0.44.3` (checked `cargo build -p clave-bar --target wasm32-wasip1`, clean
build, no warnings). Cross-checked against the vendored source
(`~/.cargo/registry/.../zellij-utils-0.44.3/src/data.rs`) before building:
- `Event::PaneUpdate(PaneManifest)` exists exactly as used.
- `PaneManifest { pub panes: HashMap<usize, Vec<PaneInfo>> }` — note the underlying
  collection is a `HashMap`, not a `BTreeMap`; the brief's `for (tab_index, panes) in
  manifest.panes` iterates either way so this didn't require a code change, but it's
  worth recording: tab-index iteration order from `PaneManifest` is **not** sorted, so
  don't rely on iteration order elsewhere (we don't — we index `pane_to_tab` by pane
  id, not by iteration position).
- `PaneInfo { pub id: u32, pub is_plugin: bool, ... }` — matches.
- `EventType::PaneUpdate` — a strum discriminant of `Event`, exists and is accepted by
  `subscribe(&[EventType::PaneUpdate])`.
- `PermissionType::ReadCliPipes` / `PermissionType::ReadApplicationState` /
  `PermissionType::ChangeApplicationState` — all three exist, accepted by
  `request_permission`.
- `fn go_to_tab(tab_index: u32)` in `zellij_tile::shim` — matches the call site
  `go_to_tab((*tab as u32) + 1)`.

No API name/shape needed to be invented or substituted.

**Permission gotcha (carries into the real §6.6 plugin):** `PaneUpdate` /
`PaneManifest` requires the **`ReadApplicationState`** permission — Zellij gates all
pane+tab state behind it (`zellij-utils 0.44.3` `src/data.rs:1086`:
`ReadApplicationState` → "Access Zellij state (Panes, Tabs and UI)"; see also Zellij's
plugin-events docs). Without it, on a CLEAN permission grant the `subscribe(&[PaneUpdate])`
silently never delivers events → `pane_to_tab` stays empty → every `clave-nav` no-ops.
The plugin therefore requests all three of `ReadCliPipes` + `ReadApplicationState` +
`ChangeApplicationState` in `load()`. (It only appeared to work without it on this
machine because the S1 cache already grants `ReadApplicationState` — a false-PASS trap
this fix closes.)

**ACTION ITEM — setup subsystem (§6.5/§6.8, packaging §7):** `clave setup` MUST grant
clave-bar ALL THREE permissions — `ReadCliPipes`, `ReadApplicationState`,
`ChangeApplicationState` — in `permissions.kdl` (not just `ReadCliPipes` as S1's note
implied). Missing `ReadApplicationState` breaks the uuid→pane→tab join on any fresh
install even though pipes still arrive.

## Fallbacks if FAIL

- **`$ZELLIJ_PANE_ID` absent/empty:** fall back to a register-while-active heuristic
  (the plugin records whichever pane most recently had a `Event::Key`/focus event
  right after a `clave spawn` was observed) or match on pane `cwd`/`title` instead of
  a numeric id (`PaneInfo` carries a `title` field; `terminal_command` may also help
  identify the spawned pane).
- **Wrong-tab focus (off-by-one or otherwise):** document the correct index mapping
  found during validation (e.g. drop the `+ 1`, or map through `get_focused_pane`/some
  other 0-based API) and update both this doc and `crates/clave-bar/src/main.rs`'s
  `go_to_tab` call site + its NOTE comment.
