# Spike S2 — uuid→pane→focus join

**Purpose:** prove the plugin can turn a displayed agent row into a focus jump:
`uuid → pane_id` (from `clave-register`) → **focus that pane** → its tab comes
forward, and that this holds across tabs.

**Verdict: PASS (2026-07-03, interactive validation on this machine).** The join
resolves correctly and the focus jump lands on the right tab via BOTH the
production keybind path (`source=Keybind`) and the `zellij pipe` shell stand-in
(`source=Cli`). Proven live + in the Zellij plugin log.

> **Mechanism changed from the plan.** The plan drove nav with
> `go_to_tab(pane_to_tab[pane] + 1)`. That was a dead end (see Finding 1). The
> working mechanism is **`focus_pane_with_id(PaneId::Terminal(pane_id))`**, which
> needs only the `uuid → pane_id` map — no `PaneManifest` / `pane_to_tab` /
> `PaneUpdate` / `ReadApplicationState`. The plugin was simplified accordingly.

## What the plugin does now (crates/clave-bar/src/main.rs)

- `load()` requests exactly `ReadCliPipes` + `ChangeApplicationState`; subscribes
  to no events.
- `pipe("clave-register", {uuid, pane_id})` → `uuid_to_pane.insert(uuid, pane_id)`.
- `pipe("clave-nav", {uuid})` → `focus_pane_with_id(PaneId::Terminal(uuid_to_pane[uuid]), false, false)`.
- Every CLI-sourced pipe is released with `unblock_cli_pipe_input(pipe_id)` so
  `zellij pipe` returns to the prompt.
- `pipe("clave-status", …)` + `render()` unchanged from S1.

## How to run (reproduce)

```bash
cargo build -p clave-bar --target wasm32-wasip1

# Launch (NOTE: `-n`, not `--layout` — with `--layout`, `--session` means "add
# tabs to an EXISTING session" and errors if absent; verified in S1). The
# `--config` adds the production-style nav keybind (see Finding 3).
zellij --config "$PWD/spikes/s2-config.kdl" -s clave-s2 -n "$PWD/spikes/layouts/s2.kdl"

# The u1/u2 panes self-register on launch (spikes/s2-register.sh).
# Production nav path — press the keybind (Ctrl+y in the throwaway config):
#   → focus jumps to the u2 tab.
# Shell stand-in for the same message:
zellij pipe --name clave-nav -- '{"uuid":"u2"}'   # → jumps to u2
zellij pipe --name clave-nav -- '{"uuid":"u1"}'   # → jumps to u1

zellij delete-session clave-s2 --force            # teardown
```

Permissions are pre-seeded in `~/Library/Caches/org.Zellij-Contributors.Zellij/permissions.kdl`
(both the `file:`- and plain-path key forms → `ReadCliPipes ChangeApplicationState`),
so there is no permission prompt on launch (see Finding 4).

## Findings

### 1. `go_to_tab` is the wrong API — use `focus_pane_with_id`
The plan's `go_to_tab((pane_to_tab[pane]) + 1)` was called with the **correct
value** (`go_to_tab(3)` for the 3rd tab, u2) from a **correct attached-client
context** (confirmed by driving it from a real keybind, not just the CLI pipe) —
and was a **silent no-op**. Cause: a 0-/1-based tab-index mismatch that the `+1`
did not resolve (Zellij's plugin `go_to_tab` did not focus the 3rd tab for
`3`). Rather than chase the exact off-by-one, switched to
`focus_pane_with_id(PaneId::Terminal(pane_id), false, false)` (zellij-tile 0.44.3
`shim.rs:1772`), which focuses the registered pane directly and lets Zellij pull
its tab forward. **No tab index, no `PaneManifest`.** This is the recommended
mechanism for the real §6.6 nav.

### 2. The join needs only `uuid → pane_id`
Because focus is by pane id, the plugin no longer needs the `PaneUpdate`
subscription, the `pane_to_tab` map, or the `ReadApplicationState` permission
(all of which the plan added solely to feed `go_to_tab`). Dropped. The whole
join is: register stores `uuid → pane_id`; nav focuses `Terminal(pane_id)`.
(§6.6 may re-introduce `PaneUpdate`/`ReadApplicationState` for OTHER reasons —
e.g. dropping closed agents from the sidebar — but not for nav.)

### 3. Production nav = keybind → `MessagePlugin`; the CLI pipe is only a driver
`spikes/s2-config.kdl` binds `Ctrl+y` to
`MessagePlugin "file:…clave-bar.wasm" { name "clave-nav"; payload "{\"uuid\":\"u2\"}" }`
→ arrives at `pipe()` with `source=Keybind` (attached-client context) and jumps
correctly. This is the real §6.6 trigger. The `zellij pipe --name clave-nav`
form (`source=Cli`) also works, but see Finding 5.

### 4. Zellij plugin permissions are ALL-OR-NOTHING per plugin
When the plugin requests a set of permissions, Zellij grants them only if the
cache holds the **entire** set under the plugin's location key; a partial match
raises the permission prompt (which is **unanswerable in a narrow/unfocused bar
pane**) and withholds **all** permissions — which then makes every `zellij pipe`
time out server-side (`Action CliPipe did not complete within 1s`). Verified:
requesting 3 perms against a key granting only `ReadCliPipes` hung everything;
seeding the exact set fixed it. Key form matters — grant under BOTH
`"file:<abs>.wasm"` and `"<abs>.wasm"`. **`clave setup` action item (§6.5/§6.8/§7):**
seed `permissions.kdl` with clave-bar's exact permission set
(`ReadCliPipes` + `ChangeApplicationState`) before/at first launch; do not rely
on the interactive prompt.

### 5. `zellij pipe` "unknown messages" flood — CLI stand-in only, harmless
Every `zellij pipe --name clave-…` invocation still triggers a server-side
`Action CliPipe did not complete within 1s timeout` + `Client sent over 1000
consecutive unknown messages … logging client out`, even with
`unblock_cli_pipe_input`. The pipe's effect (register/nav) happens regardless,
and the **keybind path is completely clean** (no flood). Since production nav is
a keybind, this is a spike-harness artifact of `zellij pipe`, not a plugin bug —
not chased further. `unblock_cli_pipe_input` was kept because it makes
`zellij pipe` return to the prompt instead of hanging.

### 6. Layout needs a visible tab strip for validation
The minimal layout renders no tab UI (clave-bar draws no chrome), so tabs and
focus were invisible. Added `zellij:tab-bar` (a built-in, auto-permitted plugin,
filtered from the join since it `is_plugin`) per-tab in `spikes/layouts/s2.kdl`
(per-tab rather than `default_tab_template`, which is parse-fragile — S1).

### 7. Env var + pane-id spaces (confirmed)
`$ZELLIJ_PANE_ID` IS exported into layout `command` panes (u1→1, u2→2, seen in
the register payloads). Registered ids are **terminal** ids; focusing via
`PaneId::Terminal(id)` is correct. (The pane-id/tab structure the log showed was
`{pane 0→tab 0, 1→tab 1, 2→tab 2}` — all terminal panes, plugin panes excluded.)

## zellij-tile 0.44.3 API notes (carry into §6.6)
- `focus_pane_with_id(pane_id: PaneId, should_float_if_hidden: bool, should_be_in_place_if_hidden: bool)`
  — `shim.rs:1772`; `PaneId::Terminal(u32)` / `PaneId::Plugin(u32)`.
- `unblock_cli_pipe_input(pipe_name_or_id: &str)` — `shim.rs:1566`; pass the
  `PipeSource::Cli(String)` id.
- `PipeSource::{Cli(String), Plugin(u32), Keybind}` — `data.rs:2993`.
- `go_to_tab(u32)` exists (`shim.rs:1356`) but its tab indexing did not focus the
  expected tab from a plugin here — avoided in favour of `focus_pane_with_id`.
